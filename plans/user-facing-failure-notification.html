1. Summary

When an error occurs at any of Kipp's three user-facing boundaries — the Telegram webhook, the LinkedIn pipeline workflow, or the scheduled cron jobs — it is logged but the end user on Telegram sees nothing. The reported symptom is a GitHub 401 during a /generate read of ideas.md, but the gap is backend-agnostic: any storage (GitHub today, Notion after #53), LLM, or router failure is silently swallowed.

This plan adds a boundary catch at each entry point that notifies the user (or operator) on Telegram with a safe, fixed message and returns a successful HTTP ack so Telegram stops retrying. A single shared function maps an unknown error to safe, user-facing wording; it never forwards err.message, response bodies, or credentials.

Backend-agnostic by design. Issue #53 (Move LinkedIn workflow to Notion) is being worked in parallel and will replace the GitHub storage layer. This fix deliberately contains no GitHub-specific wording; it keyed on error class/status only, so ~90% of the diff survives the Notion migration unchanged. Notion error text lands as a follow-up to #53.

2. Problem & Reproduction

Issue #56 reports:

(error) GithubError: GitHub read ideas.md error 401: {
  "message": "Bad credentials",
  "documentation_url": "https://docs.github.com/rest",
  "status": "401"
}

Telegram simply shows nothing as a response, leaving the user in the dark. The issue also asks "What other such errors are unhandled?"

Reproduction: with an expired/invalid GITHUB_PAT, send /generate to the bot. The webhook logs the error and returns HTTP 500 to Telegram (which retries). No message reaches the user.

3. Root Cause Analysis

One pattern, repeated at three boundaries: errors are logged but never translated into a Telegram message.

BoundaryLocationToday's behavior
Telegram webhook src/triggers/telegram-webhook.ts /generate reads ideas.md (readFile at line 184) and /add mutates it (line 224); a GithubError propagates uncaught out of handleMessage → webhook 500, Telegram retries, user sees nothing. dispatchRoutedInteraction (router / workflow.get / sendEvent failures) has the same gap.
Pipeline workflow src/linkedin/workflow.ts:107 run() catch logs and rethrows. GitHub failures in generate/archive steps and LLM failures never notify. (LinkedIn publish failures are already handled via notifyPublishFailure.)
Cron jobs src/index.ts:scheduled, src/triggers/rss.ts, src/triggers/cadence.ts GitHub 401 silently aborts the job (weekly cadence / daily RSS).
Calendar workflow already notifies (CALENDAR_FAILURE in src/calendar/agent-workflow.ts) — no change needed there.

4. Design

4.1 Shared failure-message mapper

New pure module src/runtime/user-failures.ts exporting userFacingFailureMessage(err: unknown): string. It classifies on error class/status only and never includes err.message, response bodies, or tokens. This is the single place where failure → wording, reused by the webhook, workflow, and cron.

4.2 Boundary catches

Each user-facing entry point gains one try/catch that (a) logs a logRuntime failure record, (b) sends the safe message to the known chat (best-effort — send failures are swallowed so they cannot mask the original error or re-trigger Telegram retries), and (c) returns success/acks as before. The webhook catch is placed after authorization succeeds, so malformed and unauthorized updates are never notified (§5.2); the cron catch is gated on operator configuration (§5.5).

4.3 Routing chatId into the workflow

The webhook already knows the originating chat. Add an optional chatId to WorkflowParams so a workflow that fails before its generate step resolves a chatId can still notify the requesting user; cron-triggered workflows fall back to TELEGRAM_ALLOWED_USER_ID.

5. Detailed Changes

5.1 New file — src/runtime/user-failures.ts

import { GithubError } from "../integrations/github"

export function userFacingFailureMessage(err: unknown): string {
  if (err instanceof GithubError) {
    if (err.status === 401 || err.status === 403)
      return `⚠️ Storage access was denied (HTTP ${err.status}). A credential may be expired or revoked — check the integration token and try again.`
    return `⚠️ A storage request failed (HTTP ${err.status}). Please try again shortly.`
  }
  return "⚠️ Something went wrong. Please try again shortly."
}

Class-agnostic: GithubError is today's storage error; a NotionError class added by #53 extends the same switch. No env var names, no message bodies, no Markdown-special characters (safe under Telegram's parse_mode: Markdown).

5.2 src/triggers/telegram-webhook.ts — webhook boundary

The protected catch is placed after authorization has succeeded for both update kinds, so the existing HTTP contract is preserved exactly: secret mismatch → 401, malformed body → 400, unverified user → 403. None of those paths enter the protected block, so none can trigger a Telegram notification.

  • Messages: handleMessage keeps its early returns (!msg.text / msg.from.is_bot → OK; verifyUser failure → 403) outside the try. The rest of its body is wrapped in a try/catch that, on error, calls handleBoundaryError and returns new Response("OK"). No duplicate verification is added.
  • Callback queries: handleTelegramWebhook already runs verifyUser(cq.from.id) before any work; wrap answerCallbackQuery + dispatchRoutedInteraction in a try/catch after that check, calling the same helper.
  • Shared helper handleBoundaryError(env, chatId, err): Promise<Response> — logs a logRuntime(env, { event: "telegram-update", outcome: "failed" }) record, console.errors, best-effort sendMessage(chatId, userFacingFailureMessage(err)).catch(() => {}) guarded by env.TELEGRAM_BOT_TOKEN (skipping notify when chatId is missing), and returns new Response("OK") so Telegram stops retrying.
  • Pass chatId: String(msg.chat.id) in the /generate PIPELINE_WORKFLOW.create params (line ~191).

5.4 src/linkedin/workflow.ts — workflow failure notification

  • In run() catch (line ~107), after the existing log/console.error: best-effort notify 
    const chatId = event.payload.chatId ?? this.env.TELEGRAM_ALLOWED_USER_ID.trim()
if (chatId && this.env.TELEGRAM_BOT_TOKEN) {
  await createTelegramClient(this.env.TELEGRAM_BOT_TOKEN)
    .sendMessage(chatId, userFacingFailureMessage(err))
    .catch(() => {})
}
    The operator fallback is trim()med so a whitespace-only TELEGRAM_ALLOWED_USER_ID is treated as absent, matching the cron no-operator behavior (§5.5).
  • Keep the existing throw err — Cloudflare Workflows preserves current retry/failure semantics.

5.5 src/index.ts — cron boundary

  • Wrap the scheduled() switch in a try/catch.
  • On failure the catch first records a structured logRuntime(env, { event: "scheduled-cron", outcome: "failed" }) event and console.errors, then attempts the guarded notification.
  • The notification is gated on the trimmed operator ID and a non-empty bot token: 
    const operatorChatId = env.TELEGRAM_ALLOWED_USER_ID.trim()
if (operatorChatId && env.TELEGRAM_BOT_TOKEN) {
  await createTelegramClient(env.TELEGRAM_BOT_TOKEN)
    .sendMessage(operatorChatId, userFacingFailureMessage(err))
    .catch(() => {})
}
    The trimmed string is passed directly to sendMessage (it accepts string); no Number() conversion occurs. A whitespace-only value trims to "" and follows the no-operator path, so chat 0 / Number(" ") is impossible. If the operator chat is absent, the logRuntime failure record above remains the only output and the handler returns normally.
  • Scope: this catch covers failures before workflow creation (RSS fetch, storage reads/writes inside handleRssCron / handleCadenceCron). Once a workflow is created, its own run() catch (§5.4) owns failure notification — a given workflow failure produces exactly one notification, never one from both boundaries.

6. Failure Message Content

ConditionMessage
GithubError 401 / 403⚠️ Storage access was denied (HTTP {status}). A credential may be expired or revoked — check the integration token and try again.
GithubError other⚠️ A storage request failed (HTTP {status}). Please try again shortly.
Anything else⚠️ Something went wrong. Please try again shortly.

Fixed wording only. The original error (including the GitHub response body) stays in operator-visible logs. Telegram receive-only: we never echo user content or error bodies back.

9. Out of Scope

  • Proactive token-health cron for GitHub PATs (on-error notification is the detection; YAGNI).
  • Notion-specific failure wording — deferred to #53; the mapper is structured to accept a new error class.
  • Calendar workflow (already notifies on failure) and LinkedIn publish failures (already handled by notifyPublishFailure).

10. Risks & Open Questions

  • Telegram send failure inside catch — swallowed so the webhook still returns 200 and no retry storm; the failure remains in logs.
  • Workflow re-notification on retry — accepted, deferred: a failed workflow may be retried by Cloudflare Workflows and each retry re-notifies. Failure visibility takes priority, so a durable per-workflow dedupe design is explicitly deferred as a non-blocking follow-up.
  • Unauthorized updates — the protected catch only runs after verifyUser passes, so error messages never reach unverified senders (§5.2).
  • Cron double-notification — excluded by construction: scheduled() catches only failures before workflow creation; workflow failures are owned by run()'s catch (§5.5).
  • #53 sequencing — if Notion lands first, only the GithubError branch of the mapper changes; the boundary catches and chatId plumbing carry over as-is.
