Provider-Neutral Conversation History Plan

Issue #13 extension: retain the author-facing drafting conversation across the Cloudflare Workflow approval loop, then supply it to every human-feedback revision.

Status: Ready for implementation.
Decisions captured: author-facing messages only; retain the complete transcript for the existing maximum of four feedback rounds; no post-completion persistence; the Revise More button is not a conversational user message.

1. Problem and outcome

Today the initial draft call has the style prompt, source idea, and optional source material. A later call to createReviseAgent receives only the current draft, critique items, and an optional feedback string. It therefore cannot see the original request, the style prompt, earlier drafts, or earlier author feedback.

The result will be a reusable conversation contract. A revision will send the LLM this sequence: initial system guidance, the original drafting request, every draft shown to the author, and each actual Telegram feedback message. The current review-only revision instruction remains available without treating internal critique as part of the author conversation.

2. Scope and boundaries

Each draft delivered for author review as an assistant messageInternal critique/classification exchanges in the author-facing transcript
Actual Telegram feedback as a user messageLong-running memory, summarisation, branching, or cross-workflow handoff
DeepSeek and Gemini adapters over one common contractChanging publishing, backlog, or Telegram routing behaviour

3. Target contract

Replace the current two-field prompt input with a provider-neutral message list in src/providers/llm.ts. Keep the type deliberately small and serializable so it can be held in Workflow step outputs.

export type LLMRole = "system" | "user" | "assistant"

export interface LLMMessage {
  role: LLMRole
  content: string
}

export interface GenerateOptions {
  messages: LLMMessage[]
}

export type GenerateFn = (options: GenerateOptions) => Promise<LLMResponse>

Do not include Telegram IDs, persistence concerns, provider-specific roles, or workflow fields in this type. Those belong at the integration edges. Future metadata can be added only when a concrete consumer needs it.

5. Conversation construction and agent changes

  1. Extract the initial drafting request construction from createDraftAgent into a reusable helper that returns an LLMMessage[]: style prompt (system) followed by a single user message containing the original idea/source request and the fixed length/format directive currently inlined in createDraftAgent (the "Write a concise LinkedIn post (150-300 words)…" instruction). That directive is part of the authoring request, so it belongs in the triggering user message, not a separate role.
  2. Have the draft agent generate from that list and return the draft. In PipelineWorkflow, append { role: "assistant", content: draft } before the draft is persisted/notified.
  3. Refactor createReviseAgent to accept the existing conversation plus review context. Build a new request by appending a non-author-facing revision instruction that supplies failed checks when present; append the actual human Telegram feedback as a user message only when it is non-empty.
  4. Call the generator with the resulting message list. Append the returned revised draft as the next assistant message.
  5. Keep createCritiqueAgent independent. It evaluates a draft but neither reads nor appends to the author transcript.

The revision instruction should say that the assistant must revise the latest draft in the conversation, preserve the established style and topic, and output draft text only. It should not repeat the previous draft or author feedback as string-labelled blocks; that information is already represented by message roles.

Revise More is upstream: the __revise__ sentinel originates from Telegram revise: callback_data translation outside workflow.ts. The workflow's contract is simply that a __revise__ event text adds no transcript message; only a subsequent real Telegram reply extends history. The trigger side is out of scope here but must keep emitting __revise__ as the event text.

6. Workflow state strategy

Use Cloudflare Workflow step results as the active workflow’s durable state. The generate step returns a serializable object containing both draft and messages. Each revise-N step returns the same shape with the extended transcript. Assign the returned transcript outside the step before the next wait/iteration.

Two four-round loops, one in scope: workflow.ts has two distinct for (i<4) loops — an internal critique loop inside the generate step (src/workflow.ts:57) and the human-feedback loop (src/workflow.ts:115). This plan targets only the latter; the internal critique loop is unchanged and out of scope. All step calls below use the existing stepDo wrapper (src/workflow.ts:27), not raw step.do, to preserve per-step error logging and the RPC-serializable cast.
let state = await stepDo("generate", async () => {
  const messages = createDraftConversation(...)
  const draft = await draftAgent(messages)
  return { draft, messages: [...messages, { role: "assistant", content: draft }], chatId }
})

// On actual Telegram feedback:
state = await stepDo(`revise-${i}`, async () => {
  const messages = appendHumanFeedback(state.messages, feedback)
  const draft = await reviseAgent({ messages, failedItems: [] })
  return { draft, messages: [...messages, { role: "assistant", content: draft }], chatId: state.chatId }
})

This matches the current bounded workflow: step outputs survive waits/replays, require no new binding or operational store, and avoid coupling the generic conversation abstraction to the LinkedIn/Telegram backlog format.

Do not use ideas.md as transcript storage. It is the existing business-state record, but mutable Markdown is a poor append log and would force unrelated future workflows to use GitHub. Do not use KV because its eventual consistency is the wrong default for sequential conversation state. D1 or a Durable Object becomes appropriate only when conversations must continue after a workflow completes, be queried/audited, grow beyond safe step-output sizes, or need multi-client concurrency.

7. Recorded Cloudflare storage decision and limits

Decision: use Cloudflare Workflow persisted step state for this bounded, active drafting loop. Do not introduce Durable Objects, D1, KV, R2, or GitHub-backed transcript persistence in this increment.

“Durable storage” can refer either to Workflow state or to Durable Object storage. This implementation uses the former: cached step.do() return values and durable wait/event progress. It does not use Durable Objects.

Workflow constraintCurrent limitDecision and implementation consequence
Non-stream step.do() result1 MiBApplies now. Each generate/revise result contains the complete transcript. Before returning it from a step, measure the UTF-8 byte size of its JSON-serialized form and fail clearly if it would exceed a conservative threshold (for example 900 KiB). Do not silently truncate author context.
Total persisted state per instance100 MB Free; 1 GB PaidSafe for four short review rounds, but step snapshots retain prior messages. An unbounded history grows stored state over time and must not be introduced without compaction/persistence design.
Completed-instance retention3 days Free; 30 days Paid by defaultAcceptable: the transcript is required only during the active workflow. This is explicitly not post-completion or cross-workflow memory.
Event payload1 MiBTelegram feedback is far below this. A future channel that accepts large text or files needs validation before calling sendEvent.
Steps per workflow1,024 Free; 10,000 Paid by defaultNot material for the current four-round loop. It is a future multi-turn-agent constraint.

Implement the size check in the generic conversation utility, not in the LinkedIn workflow. It should measure the exact serializable shape the workflow returns — including the chatId field alongside draft and messages, not the messages array alone — use TextEncoder for UTF-8 byte length, and include the measured size and configured limit in a safe error message. The guard is a platform-boundary validation, not a context-management policy.

Why Durable Objects are deferred

A Durable Object would add a strongly consistent, transactional SQLite-backed store and per-conversation serialisation. That is useful when history must outlive a Workflow, be queried, be shared among multiple clients, or be updated concurrently. It does not solve a current requirement and would add a binding, schema, lifecycle, and cost surface.

If a Durable Object is selected later, use one object per conversation and the SQLite backend. Its relevant constraints are a 2 MiB key/value-or-row limit, a 10 GB per-object limit on Paid (1 GB Free), and inherently single-threaded handling with a soft limit of about 1,000 requests per second per object. It must not become a global conversation bottleneck.

8. Implementation sequence

  1. Introduce LLMRole, LLMMessage, and the messages-only GenerateOptions contract. Update call sites and mocks so TypeScript identifies any remaining legacy prompt usage.
  2. Update src/providers/deepseek.ts, src/providers/gemini.ts, and their tests to validate exact message translation and role ordering.
  3. Refactor draft/revise agent APIs and unit tests around messages. Maintain the existing text-only output contract from agents.
  4. Add a generic serializable-transcript size guard. Call it immediately before every Workflow step returns transcript state; test its boundary and error behaviour.
  5. Modify src/workflow.ts so every draft/revision state transition carries the extended transcript. Ensure __revise__ adds no message and only actual text feedback is appended.
  6. Add workflow tests for first feedback and multiple feedback turns; run the full quality suite.

10. Acceptance criteria

  • A revision after Telegram feedback receives the original style prompt, original idea/source request, all earlier author-visible drafts, and all earlier actual feedback in chronological order.
  • DeepSeek and Gemini both accept the same canonical conversation input and preserve its meaning in their native APIs.
  • The transcript survives Workflow waits/replay within the existing feedback loop without external persistence.
  • Every persisted transcript is validated against a conservative Workflow step-output size threshold; oversized transcripts fail with a safe, actionable error and are never silently truncated.
  • Internal critique and the Revise More button do not appear as author messages.
  • pnpm typecheck, pnpm lint, and pnpm test pass.

11. Deferred scalability checkpoint

Before introducing a workflow with unbounded or significantly longer conversations, add a separate design pass for context limits and retention. That pass should define a provider-aware token budget, a summarisation/compaction strategy, redaction and audit requirements, and whether D1 or a Durable Object should become the persistent conversation store. It must also choose an external-storage lifecycle and retrieval strategy, rather than relying on Workflow completed-instance retention. None of those concerns should distort this bounded first implementation.
