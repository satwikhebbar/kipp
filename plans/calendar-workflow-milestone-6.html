Kipp Calendar — Milestone 6 Implementation Plan

Harden the completed Calendar v1 workflow for real webhook delivery and operational handoff. This phase closes reliability and documentation gaps without expanding Calendar product scope.

Outcome: every Calendar mutation remains deterministic and idempotent through bounded transient failures; a successful write is recovered only by bounded confirmation delivery; duplicate Telegram updates are harmless; metadata-only failure telemetry makes failures diagnosable; and a new operator can configure, deploy, validate, and troubleshoot Calendar v1 from repository documentation alone.

1. Scope and invariants

IncludedExcluded
Google transient retry correctness and backoff coverage; idempotent uncertain-write recovery; confirmation-only delivery recovery; webhook and interaction duplicate tests; safe lifecycle logs; exhaustive existing decision-branch tests; Google/Telegram/Cloudflare setup, local dev-bot smoke, deployment, and troubleshooting instructions.New Calendar capabilities, post-window management, ETag protection for manual edits, dashboards/alerts, background retries, multiple calendars, event-detail disclosure, new LLM behavior, generic workflow-runtime extraction, or changes to the approved scheduling policy.
  • Only deterministic workflow code may create, update, delete, or reconcile Calendar events. The model never sees credentials, raw Calendar API payloads, or write authority.
  • A Telegram message identity maps to one opaque Calendar event/series identity. Retries and redeliveries reuse it; a separately sent message remains an intentional new request.
  • Retry only transient network, 429, and 5xx failures, for at most two retries with bounded backoff. Authorization and permanent failures do not retry; no background retry is added.
  • After a write has succeeded, recovery may retry delivery of the deterministic confirmation only. It must never recreate, update, or re-reconcile the Calendar event merely because Telegram delivery was uncertain.
  • Logs contain opaque workflow/session/interaction identifiers, outcome category, safe HTTP/reason categories, duration, and retry count only—never request text, event data, token/OAuth material, provider bodies, or Telegram contents.

5. Documentation and deployment handoff

  1. Document the minimum Google Cloud configuration: Calendar API, OAuth Web application, exact production and local callback URIs, consent ownership, and primary-calendar-only permission boundary.
  2. Document Cloudflare configuration by secret versus non-secret variable, Durable Object/Workflow migrations, Access protection/bypass route, Telegram webhook secret, timezone, and production-safe logging settings.
  3. Provide a reproducible local dev-bot flow: isolated bot, tunnel, webhook registration, OAuth redirect origin, safe test-event naming, inspection, and mandatory cleanup.
  4. Make the pre-deploy command sequence explicit, including automated checks, required environment review, deployment, dev-bot smoke, and post-deploy log inspection.
  5. Add a troubleshooting table for unconnected/revoked Google authorization, redirect mismatch, webhook authentication failure, missing workflow/router bindings, transient Google failure, confirmation-delivery failure, stale controls, duplicate updates, and how to collect metadata-only logs.
  6. Update architecture request flows and module/deployment inventory only where the delivered retry/recovery/logging contracts change deployed behavior.
