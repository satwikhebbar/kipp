Problem

token-vault-client.ts hand-rolls the full JWT verification pipeline: base64url decode, header parsing, algorithm restriction, JWKS fetching with manual caching, key lookup by kid, kty/use enforcement, raw crypto.subtle.importKey + crypto.subtle.verify, claims parsing, and exp/nbf/iss/aud validation. Five silent try/catch blocks (lines 60, 69, 86, 94, 113) make every failure path — attack or outage — return null identically.

The 12 review/fix rounds on 2026-07-20 repeatedly surfaced the same pattern: protocol invariants that a maintained library provides for free (algorithm allowlisting, key-use enforcement, claim validation order) were being re-discovered and patched one at a time.

Design decisions

Team-scoped JWKS resolver. createRemoteJWKSet must be called with the JWKS URL at the point where env.ACCESS_TEAM is available (inside verifyAccessJwt). A single module-level resolver is impossible because env isn't available at module scope. Use a Map<string, ReturnType<typeof createRemoteJWKSet>> keyed by team domain, lazily created:

const jwksResolvers = new Map<string, ReturnType<typeof createRemoteJWKSet>>()

function getJwksResolver(teamDomain: string) {
  let r = jwksResolvers.get(teamDomain)
  if (!r) {
    r = createRemoteJWKSet(
      new URL(`https://${teamDomain}.cloudflareaccess.com/cdn-cgi/access/certs`),
    )
    jwksResolvers.set(teamDomain, r)
  }
  return r
}

Required time claims. The current code rejects tokens missing exp or nbf. jwtVerify validates these when present but doesn't require them. Pass requiredClaims: ["exp", "nbf"] to preserve the existing behavior.

JWK use policy. The current code accepts JWKs with absent use (if (jwk?.use && ...) — the guard only triggers when use is set). This is the correct default per RFC 7517 (absent use means "any use") and matches Cloudflare Access's published JWKS, which does not include use. Preserve this leniency. createRemoteJWKSet by default only returns keys suitable for the intended operation; if a key without use is excluded, document that as an intentional tightening and add a test. If included, add a test proving the absent-use key continues to work.

Adding 1 dependency

jose (panva/jose, MIT, Workers-compatible, WebCrypto-native).

Updating 1 test file

src/__tests__/token-vault-client.test.ts — Default fixture uses use: "sig" (signing-key model). A separate regression test verifies a JWK with absent use is still accepted, matching the documented policy. All 20+ existing test scenarios kept.

Keeping 2 files

  • src/token-vault.ts — Durable Object + RPC dispatcher. Application logic, not crypto protocol. Unchanged.

Public API preserved: verifyAccessJwt(request, env) and createTokenVault(env) keep same signatures. No changes to src/index.ts, src/integrations/linkedin.ts, src/triggers/linkedin-auth.ts, or src/triggers/token-check.ts.

What jose provides vs what we hand-roll

Invariant Now (hand-rolled) After (jose)
Algorithm restriction header.alg !== "RS256" (line 64) algorithms: ["RS256"] — jose rejects mismatches
Key type check jwk.kty !== "RSA" (line 73) Built into key import for requested algorithm
Key use check jwk.use !== "sig" (line 74) Built into JWKS processing (per JWA spec)
Signature verification crypto.subtle.importKey + crypto.subtle.verify (lines 76-88) Built into jwtVerify
Expiry check Date.now() > rawClaims.exp * 1000 (line 98) clockTolerance option
Not-before check Date.now() < rawClaims.nbf * 1000 (line 99) clockTolerance option
Issuer check Manual string compare (line 100) issuer option
Audience check Manual array/string compare (lines 102-105) audience option
JWKS caching Map<string, {keys, fetchedAt}> + manual staleness (lines 26-45, 1h hardcoded) createRemoteJWKSet — respects Cache-Control/Expires headers, auto-refetch
JWT format parts.length !== 3 (line 55) + manual decode Built-in
Error handling 5 silent try/catch → null blocks (lines 60, 69, 86, 94, 113) 1 try/catch around jwtVerify — jose throws typed errors for covered cases

src/__tests__/token-vault-client.test.ts

Existing test scenarios kept. Specific changes:

  • JWK generation adds use: "sig" to the public key export (signing-key fixture convention — not asserted as Cloudflare Access's production JWKS shape).
  • Add a test for a JWK without use — documents the policy decision and catches regressions if jose's filtering changes.
  • Fetch mocks for createRemoteJWKSet must return full Response objects with appropriate headers (e.g. cache-control: public, max-age=3600) and JSON body containing a { keys: [...] } payload. Existing fetch stubs that only returned { ok: true, json: () => ... } need updating.
  • Team-scoped JWKS isolation test stays but now verifies two createRemoteJWKSet resolvers in the Map and cross-team rejection.
  • Missing exp / missing nbf tests remain and verify requiredClaims enforcement.

Test Strategy

Existing tests cover:

  • No JWT header / missing header
  • Malformed JWT (not 3 parts)
  • Bad algorithm (HS256 instead of RS256)
  • Missing kid / unknown kid
  • Wrong key type (EC instead of RSA)
  • JWK with absent use (policy accepts it)
  • Wrong signature / tampered payload
  • Expired / not-yet-valid tokens
  • Wrong issuer / wrong audience
  • Array audience (valid match / no match)
  • Missing / wrong email, email not in allowlist
  • Team-scoped JWKS cache correct isolation
  • Insecure local fallback guard

All should pass after migration. Test changes detailed in the "File Changes" section above.

Risk & Mitigation

Risk Mitigation
jose is ESM-only — Worker compat? Yes. jose detects WebCrypto at runtime, works in Cloudflare Workers. No Node.js polyfills needed. Several production Workers use it.
createRemoteJWKSet caches differently than current Map (1h hardcoded) jose respects Cache-Control/Expires from the JWKS response. Access JWKS endpoint sets Cache-Control: public, max-age=3600 — same effective TTL.
New jose version breaking semantics Pin major version. jose is stable, semver. Panva is OpenID Foundation.
Bundle size increase jose is tree-shakeable. import { jwtVerify, createRemoteJWKSet } pulls only JWT/JWK modules, ~20KB gzipped.
jose may reject JWKs without use — would tighten current behavior If createRemoteJWKSet excludes keys without use, that's an intentional tightening: Cloudflare Access JWKS doesn't include use, so if jose rejects them, we need to confirm with a live test or add a compatibility shim. Documented and tested regardless of outcome.
createRemoteJWKSet requires real fetch Response objects in tests Mock builder helper (e.g. mockJwksResponse(keys)) that returns a proper Response with headers. Existing stubs are insufficient.
