Kipp Calendar — Owner-Visible Conflict Disclosure and Rescheduling

Design for GitHub issue #40: let the authenticated Calendar owner learn, on request, which existing event occupies a requested time and — only after seeing the proposed change and confirming — have Kipp move that event deterministically. This path introduces no new event detail to model context, OAuth material, or write authority, and the FreeBusy-only default experience is unchanged until the design is approved and implemented.

Outcome: the owner taps Why is this time busy?, sees a deterministic summary (title + times) of every overlapping event, and can choose to reschedule a single, non-recurring, non-all-day event. Any move requires a second explicit confirmation of the exact proposed change, is performed by deterministic workflow code with ETag concurrency and idempotent recovery, auto-creates the original request at the freed time, offers a 15-minute full-revert Undo, and is governed by a persisted phase machine that compensates or reports safely when the non-atomic writes cannot complete.

1. Scope and invariants

IncludedExcluded
Owner-initiated disclosure of the conflicting event(s) (title + times only) on the primary calendar; owner-approved, deterministic rescheduling of one existing non-recurring, non-all-day conflicting event; auto-creation of the original request at the freed time; explicit two-step confirmation; ETag-guarded move and undo; a persisted phase record that makes the non-atomic writes recoverable; opaque per-event selection; 15-minute expiry; integration/security coverage.Any automatic disclosure, move, cancel, overwrite, or deletion of an existing event; adding event detail to model context; new OAuth scopes; moving recurring-series or all-day events (disclosed but not movable); moving events on non-primary calendars; post-window management; changing the current FreeBusy-only conflict message or its defaults; changing the existing bounded list_calendar_events projection.
  • The default conflict experience is byte-for-byte unchanged. The disclosure and reschedule options are added actions; the existing best-alternative, Try another time, and Cancel flow remains the default path.
  • This path adds no new event detail to model context. The pre-existing bounded list_calendar_events projection (title + timing, used only to resolve references) is unchanged; the disclosure snapshots never enter the agent transcript or any tool input/output — they exist only in workflow-owned state and are rendered by deterministic workflow code.
  • Only the authenticated owner may see the disclosure, only by tapping the disclosure action.
  • No existing event is moved unless the owner first sees the exact proposed change and then confirms it with a dedicated button.
  • Only deterministic workflow code performs reads for disclosure and writes for rescheduling. The move is ETag-guarded, idempotent, reversible within the 15-minute interaction window, and every partial outcome is compensated or reported per §5.5.
  • Recurring-series and all-day conflicting events may be disclosed (title + times) but never rescheduled; recurring series already have their own adjustment flow.

3. Owner-visible disclosure policy

Minimum disclosed fields: the overlapping event's title and its start/end times, plus the all-day flag when set. Nothing else: never description, location, attendees, organizer, links, conferencing data, transparency/visibility state, extended properties, or raw provider metadata.

Why this is safe in Telegram

  • The disclosure is rendered by a fixed workflow template, not by the model, so event titles are plain text that cannot change behavior. No parse_mode is used, so titles cannot inject formatting, links, or markup.
  • The message is delivered only to the owner's private chat through the allow-listed Telegram flow, on demand.
  • No Calendar event link, URL, or external identifier is included.
  • Titles are untrusted data end to end: they appear only as plain text in the owner-visible body and in no button label, callback payload, model context, or log.

4.1 Opaque, durable per-event selection

The existing WorkflowInteraction carries a kind and an opaque interaction ID — never an event ID — and promptForActions already binds each action to its own random interactionId/callbackToken. The disclosure sub-flow reuses exactly this: each movable event's Reschedule action is registered under kind calendar-conflict-reschedule with its own opaque interaction ID, while the workflow keeps a server-side selection map in step state mapping that opaque ID to the snapshot ({ eventId, title, start, end, allDay, etag }). A resolved callback returns only the opaque interaction ID; the workflow looks the snapshot up in its own state. No Calendar event ID or title ever enters Telegram callback data, the router, or a button label.

  • Version / TTL: the selection map lives in workflow step state and inherits the 15-minute interaction TTL. Router versioning already invalidates superseded actions; a new evaluation or a re-entered disclosure replaces the map, so a stale button resolves to an unknown/superseded selection and yields the safe "availability changed" outcome.
  • Duplicate delivery: the router claim is idempotent, so a re-delivered callback resumes the same durable step and cannot re-issue a move. The selection is consumed on first successful resolution; a repeat resolves as already-used.
  • Label policy: button labels never contain raw titles. The existing multi-action label limit is MAX_MULTI_ACTION_LABEL_CHARACTERS = 16 (see src/calendar/agent-workflow.ts); each per-event label is derived from the event start time only (e.g. Reschedule 14:00), disambiguated with a numeric suffix when two movable events share a start time (14:00 (1), 14:00 (2)). Arbitrary-length, untrusted titles appear only in the owner-visible message body as plain text.

5. Deterministic update semantics

5.1 ETag / concurrency

  • Add an ETag-capable read and guarded patch to the Google client, used only by the reschedule/undo path. The existing create/update/reconcile paths keep their current behavior.
  • The move sends If-Match: <etag> captured from a fresh read immediately before the write. A 412 Precondition Failed is a typed precondition-failed outcome, not an error body: the workflow surfaces a safe "availability changed" message, performs no overwrite, and re-evaluates. The owner's pending choice is preserved via the existing plan/option ledger.
  • If the event was deleted or is not found (404), the workflow reports the safe "availability changed" outcome and re-evaluates; it never recreates a moved event.
  • The external-event move and restore are guarded partial updates (PATCH) that change only start/end (retaining the event's timezone), so fields that are not in the disclosure snapshot — description, location, attendees, reminders, visibility, and so on — are preserved. The existing full-PUT path remains correct for Kipp-managed events because Kipp owns every field of those events.

5.2 Idempotency

  • The move derives its identity from (event id, requested original start, proposed target start). On an uncertain write (network failure after Google applied it), the workflow re-reads the event and treats the move as complete if the event is already at the target start/end — the same verify-by-read pattern createManagedEvent already uses. No duplicate move is performed.
  • The original request is created only after the move is verified, using the existing managed-event identity (chat/message id), so its create is idempotent as today. An uncertain create is resolved by re-read before retry.
  • Undo is a full revert: restore the moved event's original times and delete the created request. Each half is idempotent via verify-by-read (restore only if not already at original; delete tolerates already-absent), and the halves are ordered per §5.5.
  • Telegram webhook redelivery of the same button resumes the same durable workflow step; it cannot re-issue a second write.

5.3 Expiry and staleness

  • All new interactions (disclosure choice, move confirmation, undo) reuse the existing 15-minute interaction TTL and router versioning. Expired or superseded buttons are ignored; version checks already reject stale callbacks.
  • The operation phase record, selection map, original start/end, and created request identity are retained only in workflow step state for the 15-minute window, then discarded. There is no post-window management.

5.4 Logging and audit

  • Logs record only opaque workflow/interaction identifiers, the persisted operation phase, outcome categories, HTTP status, and the typed concurrency outcome. Event titles, times, descriptions, locations, and ETag values are never logged.
  • Add redaction assertions that inspect captured logs and prove no title, time, or event content appears.

5.5 Recoverable phase machine for non-atomic writes

The move → create and the undo (restore → delete) sequences are not atomic. The workflow persists one RescheduleOperation phase record for the whole 15-minute recovery window, holding the moved event's opaque identity, original start/end and ETag, target start/end, the created request's managed identity, and the selection ID.

move → create:  move-pending → move-verified → create-pending → created
undo:           created → restore-pending → restored → delete-pending → undone
failure:        any phase → failed        (compensation attempted first)

5.6 Compensation and owner-facing outcomes for partial writes

ScenarioPrescribed behavior
Create fails (permanently) after the move verifiedCompensate in the same step: guarded PATCH the moved event back to its original times. If compensation verifies → phase undone; message: "I couldn't create your block, so I restored <title> to its original time." If compensation also fails (ETag conflict or transient exhausted) → phase failed; message: "I moved <title> to <target> but couldn't create your block or restore it. Please check your Calendar." No success is claimed.
Undo restore hits an ETag conflict or failsDo not delete the created request (the owner loses nothing). Phase failed; message: "I couldn't restore <title> because it changed externally. The new block stays. Please check your Calendar." Undo success is never claimed.
Undo delete fails after restore verifiedRetry the delete (idempotent) with the existing bounded transient retry; on exhaustion, phase failed with a safe message that the block may remain and to check the Calendar. Restore is not repeated.
Transient uncertainty at any guarded writeRe-read and verify the intended terminal state before advancing; never duplicate the write. Bounded retries use the existing transient policy.
Expiry or stale action during any phaseThe phase record is discarded; no further writes occur; the already-verified outcome stands. No post-window management.

Messages in this section name only fields already owner-visible (title + times) and point to the Calendar for manual inspection; they never include event IDs, ETags, or technical detail.
