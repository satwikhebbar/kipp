Kipp Calendar — Owner-Visible Conflict Disclosure and Rescheduling

Design for GitHub issue #40: let the authenticated Calendar owner learn, on request, which existing event occupies a requested time and — only after seeing the proposed change and confirming — have Kipp move that event deterministically. The model never receives event details, OAuth material, or write authority, and the FreeBusy-only default experience is unchanged until this is approved and implemented.

Outcome: the owner taps Why is this time busy?, sees a deterministic summary (title + times) of every overlapping event, and can choose to reschedule a single, non-recurring, non-all-day event. Any move requires a second explicit confirmation of the exact proposed change, is performed by deterministic workflow code with ETag concurrency and idempotent recovery, auto-creates the original request at the freed time, offers a 15-minute full-revert Undo, and leaves no model-visible or log-visible event detail.

1. Scope and invariants

IncludedExcluded
Owner-initiated disclosure of the conflicting event(s) (title + times only) on the primary calendar; owner-approved, deterministic rescheduling of one existing non-recurring, non-all-day conflicting event; auto-creation of the original request at the freed time; explicit two-step confirmation; ETag-guarded move and undo; idempotent recovery; 15-minute expiry; integration/security coverage.Any automatic disclosure, move, cancel, overwrite, or deletion of an existing event; model-visible event details; new OAuth scopes; moving recurring-series or all-day events (disclosed but not movable); moving events on non-primary calendars; post-window management; changing the current FreeBusy-only conflict message or its defaults.
  • The default conflict experience is byte-for-byte unchanged. The disclosure and reschedule options are added actions; the existing best-alternative, Try another time, and Cancel flow remains the default path.
  • The model never receives event summaries, titles, times, descriptions, locations, attendees, ETags, or raw Calendar responses. Only the authenticated owner may see the disclosure, only by tapping the disclosure action.
  • No existing event is moved unless the owner first sees the exact proposed change and then confirms it with a dedicated button.
  • Only deterministic workflow code performs reads for disclosure and writes for rescheduling. The move is ETag-guarded, idempotent, and reversible within the 15-minute interaction window.
  • Recurring-series and all-day conflicting events may be disclosed (title + times) but never rescheduled; recurring series already have their own adjustment flow.

The existing security model already provides every boundary this feature needs; no OAuth scope change is required.

3. Owner-visible disclosure policy

Minimum disclosed fields: the overlapping event's title and its start/end times, plus the all-day flag when set. Nothing else: never description, location, attendees, organizer, links, conferencing data, transparency/visibility state, extended properties, or raw provider metadata.

Start/end timesYes, on owner requestNoNo

ETagNoNoNo
Description, location, attendees, links, conferencing, extendedPropertiesNoNoNo

Why this is safe in Telegram

  • The disclosure is rendered by a fixed workflow template, not by the model, so event titles are plain text that cannot change behavior. No parse_mode is used, so titles cannot inject formatting, links, or markup.
  • The message is delivered only to the owner's private chat through the allow-listed Telegram flow, on demand.
  • No Calendar event link, URL, or external identifier is included.

Titles are treated as untrusted data end to end: the disclosure template prints them verbatim as plain text; no instruction-like content in a title can reach a prompt or a decision.

5. Deterministic update semantics

5.1 ETag / concurrency

  • Add an ETag-capable read and update to the Google client, used only by the reschedule/undo path. The existing create/update/reconcile paths keep their current behavior.
  • The move sends If-Match: <etag> captured from a fresh read immediately before the write. A 412 Precondition Failed is a typed precondition-failed outcome, not an error body: the workflow surfaces a safe "availability changed" message, performs no overwrite, and re-evaluates. The owner's pending choice is preserved via the existing plan/option ledger.
  • If the event was deleted or is not found (404), the workflow reports the safe "availability changed" outcome and re-evaluates; it never recreates a moved event.

5.2 Idempotency

  • The move derives its identity from (event id, requested original start, proposed target start). On an uncertain write (network failure after Google applied it), the workflow re-reads the event and treats the move as complete if the event is already at the target start/end — the same verify-by-read pattern createManagedEvent already uses. No duplicate move is performed.
  • The original request is created only after the move is verified, using the existing managed-event identity (chat/message id), so its create is idempotent as today. An uncertain create is resolved by re-read before retry.
  • Undo is a full revert: restore the moved event's original times and delete the created request. Each half is idempotent via verify-by-read (restore only if not already at original; delete tolerates already-absent).
  • Telegram webhook redelivery of the same button resumes the same durable workflow step; it cannot re-issue a second write.

5.3 Expiry and staleness

  • All new interactions (disclosure choice, move confirmation, undo) reuse the existing 15-minute interaction TTL and router versioning. Expired or superseded buttons are ignored; version checks already reject stale callbacks.
  • The original start/end and the created request's identity are retained only in workflow step state for the 15-minute window, then discarded. There is no post-window management.

5.4 Logging and audit

  • Logs record only opaque workflow/event identifiers, outcome categories, HTTP status, and the typed concurrency outcome. Event titles, times, descriptions, locations, and ETag values are never logged.
  • Add redaction assertions that inspect captured logs and prove no title, time, or event content appears.
