Architecture Overview

An automated LinkedIn posting pipeline running on Cloudflare Workers + Workflows (TypeScript pnpm). Orchestrates a draft-critique-revise loop using an LLM, waits for Telegram-based feedback via step.waitForEvent(), and creates a LinkedIn DRAFT post — never publishing automatically.

Key Architectural Decisions

  • Cloudflare Workflows for durable multi-step execution — step.do() for each pipeline stage, step.waitForEvent() to pause for a configurable window (default 12 hours) while waiting for Telegram replies; idle waits don't incur CPU, timeout → awaiting-feedback-expired
  • Two-repo model (public template + private data repo) so the template is open-source-ready and deployer-specific data/credentials stay private
  • Provider-agnostic LLM layer — Gemini Flash for draft/critique/classify by default, DeepSeek as a configurable budget alternative
  • State of record is ideas.md/archive.md in the private data repo, synced at each workflow state transition

Telegram Quick-Capture On-demand Yes — as raw entry No
Cadence Check Weekly (Monday 9:00) No Yes — fallback if nothing finalized in 7 days

Telegram Webhook Intent Routing

Message Pattern Intent Action
Fresh message, not a reply to bot Quick-Capture Append text as new raw idea to ideas.md
Message text is /generate Generate Command (extension) Start workflow on oldest raw idea (or reply "no raw ideas")
Reply to one of the bot's own messages Feedback / Approval Deliver event to matching workflow instance via waitForEvent

Implementation Phases

15 phases, ordered for sequential implementation and testing.

Phase 1 — Project Scaffold

8 files Project skeleton, config, types, examples, README.

  1. package.json — wrangler, typescript, vitest, hono, @google/generative-ai, @cloudflare/workers-types, @cloudflare/vitest-pool-workers
  2. wrangler.toml — Worker config, Workflow binding, 2 cron triggers (rss daily, cadence weekly), secrets declarations
  3. tsconfig.json — ESNext target, bundler module resolution, strict, Workers types
  4. .gitignore — node_modules, dist, .wrangler, .env, logs
  5. example/style-prompt.md — Generic placeholder system prompt
  6. example/ideas-template.md — Empty ideas.md structure with format comments
  7. src/types.ts — Idea, IdeaStatus (raw|drafted|awaiting-feedback|awaiting-feedback-expired|finalized), ArchivedIdea, LLMResponse, ChecklistItem, ClassificationResult, WorkflowParams, WorkflowEvent
  8. README.md — Fork → clone → data repo → BotFather → LinkedIn app → secrets → deploy

Phase 2 — LLM Provider Layer

4 files Provider-agnostic interface, Gemini and DeepSeek clients, factory.

  1. providers/llm.ts — GenerateOptions + GenerateFn type: (opts: { system?, prompt }) → Promise<LLMResponse>
  2. providers/gemini.ts — Gemini Flash via @google/generative-ai, map usage metadata
  3. providers/deepseek.ts — DeepSeek via OpenAI-compatible fetch, map native token fields
  4. providers/index.ts — Factory: createGenerator(apiKey, provider) → GenerateFn. Config resolution inlined (ternary, no separate file)

Phase 3 — GitHub Data Repo Integration

1 file GitHub Contents API read/write for the private data repo, with SHA-based conflict handling.

  1. integrations/github.ts — readFile(path) → { content, sha }, writeFile(path, content, sha) — SHA-based CAS PUT. Writes are mutation functions: read → parse → mutate → serialize → write. On 409: re-read SHA → re-parse → re-apply mutation → serialize → retry (max 3). moveToArchive(idea) — read ideas.md → remove idea entry → read archive.md → append entry → write both (idempotent: check archive for duplicate before append; if one write succeeds and the other 409s, the successful write is committed and the failed one retries independently). Error handling: 404, 401, 409 (after retries) → Telegram alert.

Phase 4 — Idea Backlog Parsing & Management

4 files + golden tests ideas.md/archive.md parsing with explicit markdown schema, state management, ID generation.

Predictable markdown schema — one fenced block per idea:

---
id: 17
status: drafted
source: substack
created: 2026-07-03T09:00:00Z
correlation:
  telegram_chat_id: "123456789"
  bot_message_id: 42
  workflow_instance_id: "wf_abc123"
---
# Idea 17

[freeform idea text]

## Draft

[multiline draft]

## Critique

- [ ] Clarity: ...
- [ ] Hook: ...
- [ ] Call to action: ...
  1. backlog/parser.ts — Parse frontmatter + body sections → typed Idea objects; serialize back to markdown. Parser golden tests for all statuses including awaiting-feedback-expired included in this phase, not deferred to Phase 12.
  2. backlog/archive.ts — Archive append, read all for duplicate-angle check
  3. backlog/manager.ts — getNextIdea(), getIdeasByStatus() (excludes awaiting-feedback-expired from raw picks), updateIdeaStatus(), moveToArchive()
  4. backlog/id-generator.ts — Monotonically increasing IDs from current max

Phase 5 — Substack RSS Trigger

1 file RSS fetch/parse, duplicate detection, idea generation via LLM.

  1. triggers/rss.ts — Fetch + parse Substack RSS → check GUID against existing → LLM call to extract 1 teaser + 2-4 sub-ideas → write to ideas.md → kickoff workflow on one

Phase 6 — Cadence Trigger

1 file Weekly fallback for quiet periods.

  1. triggers/cadence.ts — Check most recent finalized date; if >7 days ago and raw idea exists → start workflow on oldest raw. Skip if already awaiting-feedback or awaiting-feedback-expired.

Phase 7 — Telegram Integration

2 files Bot API client + webhook handler with message and callback_query routing.

  1. integrations/telegram.ts — sendMessage(), sendDraftNotification(), sendStatusUpdate(), answerCallbackQuery()
  2. triggers/telegram-webhook.ts — Webhook handler: verify secret, route by update type. callback_query: verify callback from allowed chat/user, call answerCallbackQuery, map callback data to workflow instance, send confirmation event via instance.sendEvent({ type: "confirmation", payload }). message routing: quick-capture → append to ideas.md; /generate → start workflow (extension); reply-to-bot → extract reply_to_message.message_id → look up correlation in ideas.md frontmatter → deliver event via instance.sendEvent({ type: "telegram-reply", payload }).

Phase 8 — Draft Agent (Core LLM Logic)

4 files Individual LLM-driven steps called by the workflow.

  1. agent/draft.ts — Build prompt from style-prompt + idea content (+ Substack body if linked). Single LLM call → draft text.
  2. agent/critique.ts — Hardcoded checklist. LLM evaluates each: { check, passed, feedback? }[]. Feedback only on failures, with specific actionable notes.
  3. agent/revise.ts — Current draft + failed checklist items + human feedback → revised draft. Called inside the loop (max 4 iterations).
  4. agent/classify.ts — Cheap LLM call: Telegram reply text → { action: "approve" | "feedback", feedbackText? }. No keywords/regex — natural language intent classification.

Phase 9 — LinkedIn Auth & Basic Client

3 files LinkedIn OAuth flow (redirect + callback), token persistence, and Posts API client for DRAFT creation.

  1. integrations/linkedin.ts — POST /v2/ugcPosts with lifecycleState: DRAFT, parse response body for URN
  2. triggers/linkedin-oauth.ts — Hono routes: GET /auth/linkedin (redirect to LinkedIn OAuth consent with client_id/scope/redirect_uri), GET /auth/linkedin/callback (exchange code for access+refresh tokens, store in data repo as .linkedin-tokens.json, return success page)
  3. src/index.ts (Phase 13 update) — Mount OAuth routes

Phase 10 — LinkedIn DRAFT Smoke Test

1 spike Verify DRAFT lifecycle state before wiring the workflow.

  1. Once Phase 9 is done (auth + client in hand), hardcode a test draft and POST with lifecycleState: DRAFT
  2. Manually verify the draft appears in the LinkedIn compose UI (not just in developer API responses)
  3. If DRAFT does not surface in the compose UI → the architecture needs a different final handoff (e.g. store final draft text and notify user to paste manually)
  4. If DRAFT works → proceed with confidence; Phase 11 (Workflow Orchestration) depends on this behavior

Phase 11 — Workflow Orchestration done

1 file (src/workflow.ts) The Cloudflare Workflow definition wiring the agent steps together.

  1. generate — step.do: draft → critique/revise loop (max 4, early exit) → save to backlog as awaiting-feedback
  2. notify — step.do: Send draft preview via Telegram with [Approve ✓] / [Revise More] inline buttons
  3. Wait loop (max 4): step.waitForEvent("telegram-reply", timeout: 7 days)
    • Timeout → mark idea awaiting-feedback-expired, return
    • Approve (__approve__) → linkedin-publish step.do (DRAFT via POST /v2/ugcPosts, guarded by LINKEDIN_ACCESS_TOKEN / LINKEDIN_AUTHOR_URN), then archive step.do (move idea to archive.md), then notify-published step.do (Telegram confirmation), return
    • Revise (__revise__ or custom text) → revise draft via LLM, update backlog, loop
Caveat — LinkedIn single-draft slot. LinkedIn only supports one DRAFT post at a time (7-day expiry). Creating a new LinkedIn draft via step.do("linkedin-publish") will silently overwrite any existing LinkedIn draft from a prior workflow run. The final draft text is always preserved in archive.md (Git history), so nothing is permanently lost, but the unpublished draft on LinkedIn can be replaced. Decision: this is acceptable for a single-user pipeline — only one workflow can be active at a time, and the user is expected to publish or clear the LinkedIn draft before the next approval completes. LinkedIn publish step is skipped if LINKEDIN_ACCESS_TOKEN or LINKEDIN_AUTHOR_URN are not set.

Phase 12 — LinkedIn Token Lifecycle

1 file Token refresh monitoring and expiry alerts (the LinkedIn client itself was built in Phase 9).

  1. triggers/token-check.ts — Weekly cron: check access token expiry, attempt refresh, Telegram alert if manual reauth needed

Phase 13 — Worker Entry Point

1 file hono routes wiring triggers to handlers.

  1. src/index.ts — Hono app: POST /webhook/telegram (handles both message and callback_query update types), cron /rss, cron /cadence, cron /token-check. Route → trigger handler → start/resume workflow. Event delivery via instance.sendEvent.

Phase 14 — Testing

~5 files Unit + integration tests with mocked external services.

  1. Unit tests for agent/* (mocked LLM provider)
  2. Unit tests for backlog/* (parser, manager, ID generator, including awaiting-feedback-expired status handling)
  3. Unit tests for triggers/* (mocked GitHub API, mocked RSS)
  4. Integration test: full workflow run with mocked externals

Phase 15 — Deployment & Go-Live

~5 steps Secrets, deploy, webhook registration, verification.

  1. wrangler secrets put — 6 secrets (5 if LINKEDIN_REFRESH_TOKEN unavailable)
  2. wrangler deploy
  3. Register Telegram webhook (setWebhook)
  4. Verify cron triggers active in Cloudflare dashboard
  5. End-to-end manual test with a real idea captured via Telegram

Open Questions & Risks

R1 — LinkedIn DRAFT lifecycle state. Does POST with lifecycleState: "DRAFT" actually surface as a usable draft in the LinkedIn compose UI? Needs one live test. If it doesn't work, fallback: store final draft text and open a browser-based data-uri approach, or skip to manual paste.
R2 — Refresh token availability. Is the programmatic refresh token feature enabled for Consumer-tier LinkedIn apps? If not, fallback to manual 60-day reauthorization with Telegram alerts. Confirm during app registration.
R3 — Style checklist refinement. The critique checklist in Phase 8 is a first draft. Expect adjustments after seeing real output from the chosen LLM.
R4 — Reply classification accuracy + confirmation requirement. A misclassified "approve" must never push an unwanted draft to LinkedIn. After classification returns "approve", the workflow sends a Telegram message with inline buttons: [Approve → LinkedIn DRAFT] and [Revise More]. Only on explicit button tap does the workflow proceed to create the LinkedIn draft. A false positive cannot call LinkedIn — a human must explicitly confirm.
R5 — Substack RSS interval. Daily polling is a starting guess. Adjust based on how frequently the target Substack publishes.
R6 — Concurrent workflow runs. The spec explicitly avoids multi-user concurrency (single deployer). For v1, ensure the cadence check doesn't start a second workflow if one is already in awaiting-feedback state.
