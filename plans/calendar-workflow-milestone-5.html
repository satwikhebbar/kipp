Kipp Calendar — Milestone 5 Revised Implementation Plan

Add bounded recurring Calendar blocks to the conversational workflow that now exists after Milestones 1–4. Preserve its native-tool planner, deterministic scheduling, privacy-safe conflict handling, idempotent writes, typed Telegram routing, reconnect flow, and 15-minute immediate Edit contract.

Outcome: Kipp can understand the approved recurrence forms, expand and validate the complete v1 series before writing, create one native Google recurring event plus any approved per-date exceptions, and safely correct the whole series during the immediate Edit window.

1. Why the original phase outline needs revision

The original roadmap predates the implemented Calendar conversation. Milestone 5 must extend the following established contracts rather than introduce a separate recurrence path:

  • The planner uses one bounded native-tool session and a static handoff allowlist. It preserves source-tagged dialogue fields across clarifications and conflict questions.
  • Deterministic code owns time choice, availability, reminders, writes, retries, identities, and privacy. Google event details never enter the model or Telegram conflict text.
  • The workflow already has typed 15-minute interactions for clarification, conflict choice, correction, reconnect, retry, and cancellation.
  • A stable identity derived from the original Telegram message makes one-off writes idempotent. Recurrence must extend that identity to a parent series and its exceptions.
  • Every successful write exposes immediate Edit. Recurring creation therefore is incomplete without a defined whole-series correction and exception-reconciliation contract.

  • The model may describe recurrence but never supplies raw RRULE text, reads Calendar data, or authorizes a write.
  • The start date is user-explicit and denotes the first occurrence; it is not silently interpreted as only a search lower bound.
  • Every occurrence that Kipp will create is expanded as a local civil date, converted in the configured IANA timezone, and availability-checked before any write.

  • No success confirmation is sent until the parent and every approved exception are present. Partial creation is never reported as success.

4. Recurrence domain and planner contract

  1. Keep the existing OneOffProposal and its Zod schema unchanged. Introduce a separate RecurringProposal and separate recurringProposalSchema, owned exclusively by submit_recurring_proposal. The workflow may use a result union after successful handoff validation, but the two tool input schemas do not share a permissive “calendar proposal” shape.
  2. Add submit_recurring_proposal beside the existing one-off and clarification tools. Its input has no structurally optional keys. Every conceptual field is either required outright or represented by a discriminated state such as provided, omitted, policy_default, or first_date_weekday.
  3. Use discriminated unions to make conditional requirements unambiguous. Cadence selects the exact rule shape; weekly selects named weekdays or the first-date weekday; and the end condition selects exactly one of default horizon, inclusive end date, or occurrence count. A missing key is invalid input, not an empty optional value.
  4. When a required key is absent or a union is malformed, the tool guard returns only safe validation paths and expectations to the model. The existing bounded tool session may repair the call on a later provider turn. If it still cannot produce a valid handoff, the workflow fails closed before availability or Calendar access.
  5. Extend the persisted dialogue snapshot so recurrence facts and explicit absence states survive focused questions. Missing or ambiguous first date always produces clarification, even when cadence or weekday is obvious.
  6. The LLM owns the semantic classification of explicit natural language into daily, weekly, biweekly, monthly, or bimonthly. Deterministic guards then enforce the allowlist and cross-field consistency. The model must clarify rather than guess when the phrase could map to more than one supported form.
  7. The model does not choose occurrences or conflict alternatives. It returns recurrence intent and interprets later user replies. Deterministic code expands the occurrence set, reads privacy-safe FreeBusy intervals, calculates the ratio, and selects the common-time or per-date candidates without exposing conflicting events to the model.

5. Deterministic recurrence engine

Do not begin with a handwritten recurrence engine. Start with a time-boxed dependency spike around rrule.js, which already expands and serializes RFC 5545 rules and supports the required COUNT, INTERVAL, BYDAY, BYMONTHDAY, and BYSETPOS options. Kipp supplies typed options; it never accepts the library’s natural-language or raw-RRULE parsing surfaces from the model or user.

6. Full-horizon availability and conflict decisions

expand complete bounded series
  → one FreeBusy read spanning first start through last end
  → evaluate requested common clock time on every date
     ├─ 0 conflicts: create native series
     ├─ conflicts / occurrences ≥ 50%:
     │    find nearest one common clock time free on every date
     │    → offer it, or request another series time / cancel
     └─ conflicts / occurrences < 50%:
          find nearest same-day time for each conflicting date
          → preview complete adjustment batch
          → Create with adjustments / Try another series time / Cancel
  • An explicit requested time uses the existing zero-buffer policy. A deterministically chosen or suggested time retains the existing 15-minute safety buffer.
  • A common alternative is offered only if it is valid on every occurrence. The workflow revalidates the full series after the user chooses it.
  • An adjustment batch is offered only if every conflicting occurrence has a same-day safe alternative. If even one date cannot be adjusted, Kipp falls back to the whole-series-time path.
  • The adjustment preview shows only the affected dates and proposed new times. It never names or describes the events causing conflicts.
  • All choices re-enter deterministic validation immediately before writing, so time spent in Telegram cannot authorize a stale availability result.

7. Google Calendar representation and write safety

  1. Extend the managed event contract with a parent recurrence rule and series metadata. Derive a stable parent ID/request ID from the original Telegram message. Do not assign standalone identities to normal occurrences.
  2. Create one native recurring parent using events.insert. Resolve its occurrences through events.instances, keyed by originalStartTime, and update only the approved adjusted instances.
  3. Make the write operation restartable: verify an existing matching parent before insert; enumerate instances on resume; idempotently reconcile the required exceptions; and verify the final parent/exception shape before returning success.
  4. On a permanent failure before confirmation, attempt compensating deletion of the newly created parent so the user is not left with a knowingly partial series. If cleanup also fails, emit metadata-only high-severity recovery context and a truthful failure message; never claim success.
  5. For immediate whole-series Edit, re-expand and revalidate first, then update the parent and reconcile the complete desired exception set. Remove obsolete Kipp-created exceptions by restoring them to the parent schedule; do not touch unrelated events.
Atomicity note: Google Calendar batch requests reduce connection overhead but are neither ordered nor transactional. They are not an atomicity mechanism for parent-plus-exception creation. Kipp must use stable identities, resumable reconciliation, final verification, and compensating cleanup.

8. Workflow and Telegram changes

  • Add typed recurrence state rather than encoding it into free text: requested rule, expanded dates, conflict ratio, common alternative, proposed exceptions, and current series baseline.
  • Add Calendar interaction kinds for Create with adjustments and Try another series time; reuse the established safe Cancel and reply routing semantics where their meaning is identical.
  • Confirmation includes title, first occurrence, local time, duration, human-readable cadence, bounded end/count, reminder, number of occurrences, and adjustment count. It does not expose an event link.
  • Edit replies retain the persisted whole-series baseline, not merely the first occurrence. A correction is replanned through the same bounded native-tool contract and revalidated like a new request.
  • Authorization recovery remains explicit and one-shot. Retry resumes the same stable series identity and reconciliation operation.
