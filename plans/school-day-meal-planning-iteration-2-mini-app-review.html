School-Day Meal Planning — Iteration 2

Telegram Mini App plan review and feedback

Decision: The existing Kipp bot opens a same-origin Telegram Mini App as the phone-friendly visual review surface. Telegram remains the only conversation, clarification, progress, and new-plan-notification surface. The Mini App never runs the planner and never treats device storage as canonical state.

Goal and boundary

An authorized parent opens the persisted active meal-plan version from a contextual Review this week's plan Telegram Web App button, scans it on a phone, collects local drafts against either an individual day/meal cell or the weekly plan as a whole, and explicitly hands one version-bound batch to the live MealPlanningWorkflow. Acceptance is acknowledged, but the app never implies that a new plan already exists.

This extends the merged versioned Telegram-first workflow. It does not change evaluation/planning semantics, profile editing, multi-bot behavior, or the Telegram clarification loop. The existing Give feedback callback remains a conversational fallback.

Authority and launch

  • Add MINI_APP_ORIGIN as a text runtime variable. It supplies the public HTTPS origin only; the launch URL contains no plan, chat, user, or version identifier.
  • After a plan version is successfully persisted, add a web_app button beside the existing feedback callback. Initial and revised plan messages therefore link only to immutable persisted versions.
  • The same-origin HTML shell may render in a normal browser, but it contains no plan data and explains that Telegram authentication is required.
  • When the persisted plan message gains its button, create/refresh a durable review-context mapping for the intended verified Telegram user, originating private chat, plan, and week. A launch resolves its chat only through that server-side mapping—never from optional initData chat fields or by assuming a user ID is a chat ID. Future household/group support needs an explicit membership mapping.
  • The client sends only raw Telegram.WebApp.initData to create a session. The server reconstructs Telegram’s canonical sorted data-check string and verifies its two-stage HMAC using TELEGRAM_BOT_TOKEN; it rejects malformed data, a timestamp more than ten minutes old or one minute in the future, replayed fingerprints, and mismatches before authorizing the verified user.
  • Short-lived opaque server sessions bind the verified user and resolved review context. Every read/write derives authority from that record, never from initDataUnsafe, route parameters, browser claims, or client-supplied identifiers. Keep the token only in page memory and an HTTPS Authorization header; never put it in a URL, DeviceStorage, or logs. Set Cache-Control: no-store and log only metadata, never raw launch data or feedback text.

Review experience

  • Expose a client-safe DTO over the persisted active plan: schedule, week/version, meal grid, preparation state, policy/trade-off cues, and optional recipe-video metadata. Never expose workflow IDs, interaction tokens, raw provider material, or unrelated rows.
  • Make the authenticated active-plan read discriminated: return a ready DTO only for an active plan in the current planning week; otherwise return a data-free empty response with the current week label. No active plan is expected, not an error or a reason to invent a blank plan.
  • Use the supplied screenshot as the directional baseline: a dark Telegram-native rounded plan card, compact Kipp/week header, six-day date selector, selected-day preparation summary, and stacked glanceable meal cells. Keep it designed for Telegram phone viewports, themes, safe areas, main/back buttons, and closing confirmation. Each cell has a Change action and a detail sheet with ingredients, cook/prep information, substitutions/easy buys, trade-offs, and opt-in external recipe links.
  • Keep every Monday–Saturday date visible. A holiday with no persisted meals is visibly unavailable and not clickable/focusable, with an accessible “No meals planned” label; it has no empty board or feedback action. A half-day is a normal selectable date with no special date state: it renders the meal subset and preparation cues supplied by its persisted schedule.
  • Build DOM nodes from dynamic data instead of injecting HTML.
  • Visibly distinguish the persisted active version, unsent Feedback ready drafts, and Feedback sent — continue in Telegram. Support two explicit draft targets: a stored day/meal cell and the whole weekly plan (for example, “too many new dishes”). Put Change plan at the right of the top header panel; it opens a plan-target draft, while each cell’s Change opens a cell-target draft. Keep each target visible in the draft summary; neither kind edits a cell directly. Session expiry, unavailable plan, and conflicts are recoverable without disclosure.
  • For an empty response, show a first-use/missed-week state: “No plan for this week yet,” with a clear handback to Telegram to send /mealplan (a Telegram deep link where supported and a copyable command fallback). Do not render a board, drafts, or feedback submission controls. This covers first launch, an old review button, and a Monday launch before a weekly plan is created.

Local draft policy

  • Store only discriminated { target: { kind: "cell", day, slot }, text } or { target: { kind: "plan" }, text } drafts in Telegram DeviceStorage, keyed by the server-returned plan ID and exact version. A browser-storage fallback is for local development only.
  • Restore only the matching key and label restored drafts. Clear drafts after submit, explicit discard, conflict/newer version, or a different plan/version.
  • State clearly that drafts are device-local, non-canonical, and not cross-device.

Durable feedback acceptance and recovery

Evolve the existing feedback_batch into the sole durable feedback record. It is inserted atomically when HTTP accepts feedback, then tracks its lifecycle until a revision uses it. This replaces the current “created only with a successful revision” behavior without adding a second feedback ledger.

Single feedback record

A forward-only migration extends feedback_batch with authoritative chat_id, workflow_instance_id, and week_end; client idempotency key; status; safe failure category; one-time failure-notification timestamp; and status timestamps. It uses a server-generated batch ID and unique (plan_id, idempotency_key). The same typed store owns bounded replay fingerprints and review contexts; it stores no browser credentials, transcripts, or raw provider failures.

Acceptance

acceptMiniAppFeedback derives the chat from the server session, atomically verifies that the exact plan/version is active, and validates each discriminated target: a plan target needs no cell, while a cell target must exist in the persisted schedule/grid. It bounds text/items, normalizes target/item IDs server-side, and persists target kind so the workflow can distinguish whole-plan guidance from cell-specific feedback. It inserts or returns the same accepted feedback_batch for an identical retry; key reuse with a different payload fails. A stale base returns 409 with a safe current-plan summary and changes neither plan nor feedback state.

Feedback-batch state machine

StateMeaning
acceptedPersisted and ready for its immediate workflow handoff.
deliveredsendEvent accepted; awaiting an atomic workflow claim.
processingThe one atomic workflow claim owns the revision.
consumedThe plan promotion and immutable feedback batch committed.
stale, failedTruthful terminal states; one guarded Telegram notification may be sent.
  • startFeedbackBatch(batchId) reads its stored workflow pointer and immediately calls get(instanceId)/sendEvent; it never uses browser input or a fresh active-plan lookup. Success records delivered.
  • A catchable dispatch exception records failed with a safe category and sends one guarded Telegram outcome that feedback was received but could not be applied. The HTTP response is equally truthful.

Workflow exception handling

Key invariant: a duplicate event cannot create a second revision, and every catchable failure produces one safe parent-facing outcome.
  • claimFeedbackBatchForWorkflow(batchId, instanceId, now) atomically moves a delivered batch to processing and validates the active base. A duplicate/delayed event sees an already-claimed or terminal batch and does nothing.
  • Catch workflow agent, evaluator, persistence, and status errors. Atomically mark a non-terminal batch failed, claim the one notification marker, and send a safe Telegram outcome without provider internals.
  • The promotion transaction keeps the plan-version CAS, feedback-batch association, and transition to consumed together.
  • There is no cron or automatic retry in this iteration. A process termination outside catchable code may leave a batch in delivered/processing; recovery of that case is explicitly deferred.

Implementation sequence

  1. Contracts and runtime: add MINI_APP_ORIGIN to Env, runtime-variable contract, local/prod provisioning, D1 migration/store/fake, the evolved sole feedback_batch lifecycle, private-chat review contexts, and replay-fingerprint expiry. Do not add a Mini App cron.
  2. Server boundary: add Mini App auth, DTO, schemas, memory-only session/read/batch routes (including the current-week ready-or-empty response), no-store headers, metadata-only logging, immediate start, atomic workflow claim, and catchable-error handling.
  3. Telegram/workflow: extend the event contract with the server-owned feedback_batch ID and a discriminated plan-or-cell feedback target, integrate claim/promotion/failure notification, and add the post-persist contextual Web App keyboard action plus its server-side review context.
  4. Client: add a small dependency-free phone-first Mini App with the no-plan /mealplan handback, version-keyed drafts only for ready plans, explicit batch submit, conflict handling, handoff confirmation, and close.
  5. Evidence: complete automated coverage, manual Android/iOS Telegram checks, documentation, and repository quality gates.

Acceptance evidence

  • Auth tests cover Telegram’s canonical HMAC, valid/tampered/malformed/expired/future/replayed launch data, replay expiry, unauthorized user, session expiry, constant-time comparison behavior, and no sensitive launch/token/feedback logging.
  • Store tests cover review-context authorization (including user-to-wrong-chat denial), valid plan-level feedback, exact cell-target validation, malformed/nonexistent target rejection, idempotency mismatch, stale/cross-chat isolation, atomic workflow claim, one-time failure notification, and promotion association.
  • Route/workflow/integration tests cover unauthenticated requests, memory-only session token transport, no-store responses, safe ready and current-week empty DTOs, 202/409, review keyboard, duplicate delivery, clarification, and a fresh review link only after persistence.
  • Explicitly simulate immediate get/sendEvent, agent/evaluator, and persistence exceptions after batch acceptance: each must mark the batch failed, create no revision, and send exactly one truthful Telegram outcome. Prove duplicate/delayed events cannot claim a batch twice, and document that a Worker termination outside catchable code has no automatic recovery in this iteration.
  • Client checks cover the screenshot-baseline header, six-day selector, day summary, and stacked cells; a no-meal holiday is visible but cannot be selected or receive feedback; a half-day is selectable and renders its schedule-defined meal subset without a special date state; top-panel Change plan and per-cell Change create the correct target; draft creation, visible summaries, restoration/invalidation; first-use and missed-Monday no-plan handback with no feedback controls; batch state; conflict UI; and no client-controlled authority or forged target. Manually verify public HTTPS launches in Telegram on Android and iOS, both themes, keyboard/safe-area changes, and close/reopen recovery.
  • Run pnpm lint, pnpm run docs, pnpm typecheck, pnpm test, and pnpm deploy:check once runtime values are provisioned.

Definition of done

An authorized configured parent can inspect a persisted plan, submit one local version-scoped batch containing plan-level and/or cell-level feedback exactly once, and continue in Telegram until a new plan version is persisted. Server authentication and authorization govern every request; drafts never become canonical; stale/duplicate actions cannot overwrite a newer plan; and review links never refer to unpersisted plans.
