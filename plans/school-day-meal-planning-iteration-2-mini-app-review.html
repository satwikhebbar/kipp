School-Day Meal Planning — Iteration 2

Telegram Mini App plan review and feedback

Decision: The existing Kipp bot opens a same-origin Telegram Mini App as the phone-friendly visual review surface. Telegram remains the only conversation, clarification, progress, and new-plan-notification surface. The Mini App never runs the planner and never treats device storage as canonical state.

Goal and boundary

An authorized parent opens the persisted active meal-plan version from a contextual Review this week's plan Telegram Web App button, scans it on a phone, collects several local drafts, and explicitly hands one version-bound batch to the live MealPlanningWorkflow. Acceptance is acknowledged, but the app never implies that a new plan already exists.

This extends the merged versioned Telegram-first workflow. It does not change evaluation/planning semantics, profile editing, multi-bot behavior, or the Telegram clarification loop. The existing Give feedback callback remains a conversational fallback.

Authority and launch

  • Add MINI_APP_ORIGIN as a text runtime variable. It supplies the public HTTPS origin only; the launch URL contains no plan, chat, user, or version identifier.
  • After a plan version is successfully persisted, add a web_app button beside the existing feedback callback. Initial and revised plan messages therefore link only to immutable persisted versions.
  • The same-origin HTML shell may render in a normal browser, but it contains no plan data and explains that Telegram authentication is required.
  • The client sends only raw Telegram.WebApp.initData to create a session. The server verifies Telegram's data-check HMAC using TELEGRAM_BOT_TOKEN, rejects malformed, expired, future, replayed, or mismatched data, and authorizes the verified user against TELEGRAM_ALLOWED_USER_ID.
  • Short-lived opaque server sessions bind the verified user and configured chat. Every read/write derives authority from that record, never from initDataUnsafe, route parameters, browser claims, or client-supplied identifiers.

Review experience

  • Expose a client-safe DTO over the persisted active plan: schedule, week/version, meal grid, preparation state, policy/trade-off cues, and optional recipe-video metadata. Never expose workflow IDs, interaction tokens, raw provider material, or unrelated rows.
  • Render a compact Monday–Saturday board designed for Telegram phone viewports, themes, safe areas, main/back buttons, and closing confirmation. Each cell is glanceable; a detail sheet supplies ingredients, cook/prep information, substitutions/easy buys, trade-offs, and opt-in external recipe links.
  • Build DOM nodes from dynamic data instead of injecting HTML.
  • Visibly distinguish the persisted active version, unsent Feedback ready drafts, and Feedback sent — continue in Telegram. Session expiry, unavailable plan, and conflicts are recoverable without disclosure.

Local draft policy

  • Store only { day, slot, text } drafts in Telegram DeviceStorage, keyed by the server-returned plan ID and exact version. A browser-storage fallback is for local development only.
  • Restore only the matching key and label restored drafts. Clear drafts after submit, explicit discard, conflict/newer version, or a different plan/version.
  • State clearly that drafts are device-local, non-canonical, and not cross-device.

Durable feedback acceptance and recovery

The existing immutable feedback_batch is written only when a revision succeeds. A separate durable submission ledger is required to make HTTP acceptance idempotent while planning or clarification is still in progress.

Ledger

An append-only migration adds meal_feedback_submission. Each row stores a server-generated ID; authoritative chat_id, plan_id, workflow_instance_id, and week_end copied from the active plan; base version; normalized scoped items; the client idempotency key; lease/retry fields; terminal metadata; and monotonic processing_claim_generation. It has a unique (plan_id, idempotency_key) constraint and stores neither browser credentials, transcripts, nor raw provider failures.

Acceptance

acceptMiniAppFeedback derives the chat from the server session, atomically verifies that the exact plan/version is active, validates all day/slot targets against the persisted schedule/grid, bounds text/items, and normalizes item IDs server-side. It inserts or returns the same submission for an identical retry; key reuse with a different payload fails. A stale base returns 409 with a safe current-plan summary and changes neither plan nor feedback state.

Dispatch state machine

StateMeaning
pendingAccepted, awaiting a dispatch lease.
dispatchingA single immediate or cron dispatcher owns a short dispatch lease.
deliveredsendEvent accepted; awaiting an atomic workflow claim.
processingA fenced workflow generation owns the bounded revision.
consumedThe plan promotion and immutable feedback batch committed.
stale, expired, failedTruthful terminal states; one guarded Telegram notification may be sent.
  • claimFeedbackDispatch(now) atomically leases an eligible row, increments attempts, and returns its stored workflow pointer and expected base. Dispatch never uses browser input or a fresh active-plan lookup.
  • The HTTP route dispatches immediately for latency. A five-minute Worker cron is the durable recovery owner and uses the same lease operation, preventing concurrent route/cron/restart dispatch.
  • Failed get/sendEvent returns a row to pending with capped exponential backoff (1, 5, 15, 30, then 60 minutes) and metadata-only logs. Reaching the stored week end marks expired; bounded retry/deadline exhaustion marks failed. A one-time guarded Telegram outcome explains that the plan ended, is stale, or that accepted feedback was not applied.

Workflow fencing

Key invariant: an execution that has lost its processing generation cannot persist a revision or notify the parent.
  • claimMiniAppSubmissionForWorkflow(submissionId, instanceId, now) atomically moves a delivered row to processing, increments and returns the claim generation, grants a lease covering the bounded agent plus clarification wait, and validates the active base in the same transaction.
  • The workflow renews its exact generation before work-producing durable steps and immediately before persistence or Telegram status. Failed renewal means it stops without more planning, persistence, or notification.
  • Only a genuinely expired processing lease can be returned to pending. Recovery receives the next generation. Every workflow-owned renewal, terminal transition, terminal-notification claim, and promotion transaction requires matching processing state, generation, and unexpired lease.
  • The promotion transaction fences the plan-version CAS, feedback-batch association, and transition to consumed together. A preempted execution cannot promote or send duplicate status; only the current generation can do either.

Implementation sequence

  1. Contracts and runtime: add MINI_APP_ORIGIN to Env, runtime-variable contract, local/prod provisioning, D1 migration/store/fake, fenced leases, and the five-minute cron in wrangler.prod.toml.
  2. Server boundary: add Mini App auth, DTO, schemas, session/read/batch routes, immediate dispatcher, cron recovery, and workflow claim/renew/complete contracts.
  3. Telegram/workflow: integrate fenced event claim/promotion/notifications and add the post-persist contextual Web App keyboard action.
  4. Client: add a small dependency-free phone-first Mini App with version-keyed drafts, explicit batch submit, conflict handling, handoff confirmation, and close.
  5. Evidence: complete automated coverage, manual Android/iOS Telegram checks, documentation, and repository quality gates.

Acceptance evidence

  • Auth tests cover valid/tampered/malformed/expired/future/replayed launch data, unauthorized user, session expiry, and constant-time comparison behavior.
  • Store tests cover authorization, target validation, idempotency mismatch, stale/cross-chat isolation, leases/backoff, fenced claim/renewal, terminal notifications, and promotion association.
  • Route/workflow/integration tests cover unauthenticated requests, safe DTOs, 202/409, review keyboard, duplicate delivery, clarification, and a fresh review link only after persistence.
  • Explicitly simulate: accepted row committed → dispatch failure → restart/cron recovery → exactly one workflow claim/revision and feedback batch, or one truthful terminal message. Also reclaim a first workflow's processing lease and resume it: only the newer fencing generation may work, promote, or notify.
  • Client checks cover grid/details, draft restoration/invalidation, batch state, conflict UI, and no client-controlled authority. Manually verify public HTTPS launches in Telegram on Android and iOS, both themes, keyboard/safe-area changes, and close/reopen recovery.
  • Run pnpm lint, pnpm run docs, pnpm typecheck, pnpm test, and pnpm deploy:check once runtime values are provisioned.

Definition of done

An authorized configured parent can inspect a persisted plan, submit one local version-scoped batch exactly once, and continue in Telegram until a new plan version is persisted. Server authentication and authorization govern every request; drafts never become canonical; stale/duplicate actions cannot overwrite a newer plan; and review links never refer to unpersisted plans.
