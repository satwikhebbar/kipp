Kipp Calendar — Milestone 3 Implementation Plan

Complete the one-off conversational contract: bounded Calendar interactions, immediate correction, and reconnect-and-Retry. Recurrence is explicitly excluded.

Outcome: one Calendar request can safely pause and resume for a focused clarification, private conflict choice, correction, or authorization recovery. Every state is bound to one chat, interaction version, workflow instance, and 15-minute expiry.

1. Scope and invariants

IncludedExcluded
Focused date/time/duration clarification; explicit-conflict actions; natural-language replacement; defaulted reminder/description; confirmation with 15-minute Edit and reconfirmation; expired authorization reconnect plus user-initiated one-shot Retry.Recurrence, post-window management/cancellation, multi-calendar access, Calendar details in prompts/messages, long-term memory, ETags, and LinkedIn behavior changes.
  • Calendar writes remain deterministic code and retain the original Telegram-message identity, so resumption cannot duplicate an event.
  • Every interaction expires after 15 minutes. Old controls and unrelated messages are ignored.
  • Conflict text never names an existing event. The model never sees event details, OAuth data, or write authority.
  • A reconnect creates a new OAuth attempt; only the explicit Retry control resumes one retained request, and makes one attempt.

3. Calendar workflow and scheduling changes

  1. Refactor planning into a testable operation that accepts the original request plus a narrowly scoped follow-up/correction, while retaining exactly one terminal planner action.
  2. Return structured scheduling outcomes: clarification, conflict with a safe best alternative when one exists, authorization recovery, failure, or a write-ready proposal. Add deterministic validation for the one-off date horizon, past dates, explicit-time constraints, duration grid, reminder bounds, and permitted description/location fields.
  3. Render compact messages that label chosen/estimated values and include reminder details. Use inline buttons only for fixed safe alternatives/actions; replacement and correction always require a reply to the registered bot message.
  4. After each successful write, register a single newest Edit action. Reconfirmation replaces prior active Calendar edit state. An expired or stale button must be harmless.
  5. For auth failures, send setup/reconnect guidance and retain the original request only for 15 minutes. The OAuth callback does not automatically create anything; it exposes a Retry action.

4. Telegram and router integration

Add Calendar kinds for clarification, replacement-time, edit feedback, conflict choices, reconnect retry/cancel, and edit. Generalize router replacement so a new active Calendar interaction invalidates its predecessor without removing LinkedIn’s active revision flow. Dispatch by workflow kind/binding, preserving existing callback acknowledgement and allow-user checks.

Privacy guard: callback payloads remain opaque; outgoing conflict messages may state only that the requested time is unavailable and a computed alternative. No Calendar title, participant, or event field from an existing event crosses this boundary.
