Calendar core for safe, clear, conflict-free one-off personal blocks. This is the implementation-ready plan for Milestone 2 of the approved Calendar roadmap.

A clear request is auto-booked only when all required event fields are confidently known or safely inferred and its proposed slot is conflict-free. The model never receives raw Calendar events, OAuth material, or a direct event-write capability.

2. Target architecture

Workflow and Telegram entry point

Add a separate CalendarWorkflow, bound as CALENDAR_WORKFLOW. The existing PipelineWorkflow, LinkedIn routes, and interaction-router behavior remain unchanged. The Telegram webhook recognizes /calendar: a bare command produces static help without an LLM call; a command with text starts the Calendar Workflow with the Telegram chat/message identity and request text.

Milestone 2 has no interactive wait state. Success, non-clear input, unavailable Calendar authorization, explicit-time conflict, and safe provider/integration failures return a single final Telegram message. This lets the Calendar workflow run to completion without changing the shared Interaction Router; Milestone 3 will generalize interactive routing.

Bounded planning runtime

Extract the smallest shared, workflow-scoped native-tool runner justified by Calendar: a serializable canonical conversation, static allowlist, maximum three provider turns and four tool calls, schema validation, and safe redacted errors. It is not a general autonomous agent framework.

Telegram request → CalendarWorkflow
  → deterministic request/time guard
  → bounded model planning loop
       ↳ get_available_slots (free candidate intervals only)
       ↳ submit_one_off_proposal (structured proposal only)
  → deterministic validation and Calendar write
  → Telegram confirmation

get_available_slots is the sole model-visible Calendar read: it returns candidate free intervals, never event titles, attendees, descriptions, locations, or raw busy intervals. submit_one_off_proposal validates a structured candidate but does not write to Google. The workflow alone performs the final write after deterministic policy checks.

3. Google authorization and token storage

Add Cloudflare-Access-protected setup and callback routes: /setup/google-calendar and /auth/google-calendar/callback. The authorization code exchange requests only:

  • https://www.googleapis.com/auth/calendar.events.owned for managed events on owned calendars;
  • https://www.googleapis.com/auth/calendar.events.freebusy for availability-only reads.

Use offline access and securely state-bound authorization. Extend the existing encrypted Token Vault through a provider namespace so existing LinkedIn token/state keys and behavior remain intact. Calendar tokens, refresh state, and rewrap support live under a Calendar namespace; OAuth state is single-use and cannot cross providers. A Calendar client silently refreshes an expired access token. If authorization cannot be used, Milestone 2 sends a safe setup instruction; reconnect-and-resume belongs to Milestone 3.

Required deployment configuration: Google client ID/secret, an authorized redirect origin, and TIMEZONE. Update local/development configuration to Asia/Kolkata; configuration, not individual events, controls the user timezone.

4. Calendar client and event contract

OperationContract
getBusyIntervalsQuery the primary calendar's FreeBusy endpoint for bounded local-time windows; return only normalized busy intervals to deterministic code.
findManagedEventRetrieve the deterministic event ID after an ambiguous write result and verify Kipp metadata before treating the event as created.
createManagedEventCreate exactly one primary-calendar event with an explicit safe ID; classify transient failures (network, rate limit, 5xx) for at most two short retries.

Derive the Google event ID from a versioned Kipp namespace plus Telegram chat/message identity using a lower-case base32hex-safe hash. It must be stable across Workflow retries but unguessable in normal use. On a duplicate/ambiguous result, fetch the ID and require matching kipp.requestId before reporting success; never create a second event.

5. Scheduling policy implemented in this milestone

Introduce a runtime-safe timezone utility (not host-local Date interpretation) to represent local dates, times, and 15-minute slots. The LLM submits a typed proposal containing title, local date, time or window, duration, useful description/location, reminder class, and uncertainty flags. Deterministic code accepts it only if it satisfies the product specification.

PolicyMilestone 2 behavior
Explicit time/dateHonor it when free. A conflict is reported safely; no event is moved or cancelled and no interactive choice is offered yet.
Inferred schedulingSearch 08:30–22:30, prefer 19:00–21:30, on a 15-minute grid. Today's slots begin no earlier than now + 30 minutes. For an inferred-time conflict, automatically select the closest suitable alternative on the requested date.
Duration and time confidenceUse generic sensible defaults (for example, personal call 30 minutes; professional call 15 minutes). Auto-select a time only up to 30 minutes. Longer or social/family requests without a usable time require clarification.
BuffersFor inferred blocks only, availability includes a 15-minute buffer before and after. The buffer does not create a second Calendar event and does not alter the event's visible duration.
ReminderTen minutes for ordinary blocks; one hour for family/social, school pickup, appointments, recurring maintenance, and physical activities; an explicit user instruction wins.

Only a confidently inferred, conflict-free (or automatically shifted inferred) one-off is written. Non-inferable date/time, unclear intent, or a schedule outside policy produces a concise request for the missing detail.

6. Implementation sequence

  1. Establish Calendar contracts. Add Calendar types, environment bindings, safe provider namespacing to Token Vault, shared timezone configuration, test fixtures, and Google OAuth route skeletons. Preserve every existing LinkedIn token path and test.
  2. Implement OAuth and client boundary. Add Access-gated setup/callback, state exchange, encrypted Calendar credentials, silent refresh, primary FreeBusy, primary event retrieval/insert, response validation, retry classification, and no-secret logs.
  3. Add deterministic scheduling primitives. Implement local-time parsing, date/window policy, slot generation, buffer-aware availability checks, generic duration/reminder defaults, deterministic IDs, Kipp event projection, and idempotent write recovery.
  4. Extract bounded planner. Add the reusable native-tool loop with exact limits and tests. Define the Calendar-only get_available_slots and submit_one_off_proposal tools; neither has write authority.
  5. Build CalendarWorkflow. Connect request classification, safe availability candidate generation, model planning, deterministic final validation, Calendar write, and confirmation. Ensure all completed steps produce stable retry inputs and outputs.
  6. Wire Telegram. Route /calendar to the new workflow, render static bare-command help, retain existing /add and /generate behavior, and extend unknown-command help.
  7. Document and smoke test. Add deployment prerequisites and a dev-bot procedure. Create a labeled, short-lived primary-calendar test event, verify its fields/reminder/metadata, and clean it up manually after the smoke test.

8. Recorded decisions

  • One connected Google account and primary calendar only.
  • Google scopes are calendar.events.owned and calendar.events.freebusy, with no broader Calendar scope.
  • TIMEZONE is shared workflow configuration, initial value Asia/Kolkata.
  • M2 auto-books only clear safe one-off requests; all conversational resolution moves to M3.
  • The Calendar write remains deterministic workflow code, outside the LLM tool allowlist.
  • LinkedIn stays unchanged in this milestone.
