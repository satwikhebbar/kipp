Decision proposal · research only

Storage for Kipp’s ideas, knowledge, and future tasks

A comparison of ten credible homes for Kipp data, with a recommendation that preserves Markdown and makes each idea independently addressable.

Prepared 29 July 2026 · Random-access requirement refined 11 August 2026 · Scope: exploration for GitHub issue #7; no implementation work is proposed or performed.

Executive recommendation

Recommend Notion as the primary human-facing store: model Ideas, Tasks, Projects, and Sources as related databases/pages, and have Kipp use a bounded queued integration. Keep scheduled Markdown exports as a portable backup and agent-ingestion source—not as the transactional write path.

The earlier Git-first recommendation was incorrect for this deployment model. Kipp currently writes through GitHub’s Contents API; each write creates a commit. A capture, status transition, generated draft, or archive action would therefore produce repository-history noise, and a multi-record change has no database transaction. This is a material ergonomic and operational cost, not a minor footnote.

Notion best satisfies the combined personal-productivity brief: a usable inbox, relational organization, external TODO tracking, and a knowledge base in one place. Its average 3 request/second API limit is acceptable for an individual workflow if Kipp queues and batches work. If long-term runtime correctness, transactions, and high-volume agent retrieval later outrank the all-in-one UI, make a separate database-backend decision and project tasks into Notion or Linear. Choose Obsidian only when open local Markdown/offline ownership is the deciding requirement and accept a separate task system.

What the issue is really asking the store to do

Kipp’s current architecture keeps active ideas in ideas.md and finalized ideas in archive.md, read and written through GitHub’s Contents API. That is a sound small-system baseline, but each file is both a human document and a mutable database table. As it grows, finding or mutating one idea requires parsing the whole collection and risks unrelated write conflicts.

  • Addressability: retrieve, update, or link one idea without scanning a giant document.
  • Human usability: capture and browse ideas, drafts, sources, and status comfortably.
  • Agent readiness: provide stable IDs, metadata filters, full text, and an export/indexing path for search or vectors.
  • Future task system: support externally visible TODOs, reminders, status, and links back to the source idea.
  • Personal ownership: avoid locking years of notes into an opaque, difficult-to-export format.
  • Operational fit: keep Cloudflare Worker integration reliable, bounded, and secure.

Non-sequential idea access is a hard requirement

Kipp must be able to draft, revise, archive, or link any idea—not merely the next idea in capture order. A long Markdown document, a vector search result, or a chronological archive is therefore not an adequate primary lookup mechanism. Vectors may help discover related material, but they must not decide which record an edit targets.

Do the leading choices support it? Yes. Notion is still the strongest all-round choice because a single record is both a queryable database row and a full KB page. The current two-file design does not qualify: finding an item entails parsing collection content.

Focused choice: Notion vs Coda vs Airtable for Kipp’s knowledge base

All three can hold an Ideas/Tasks/Sources model. They are not equivalent for an agent-maintained knowledge base: Notion is page-first with a native Markdown API; Coda is a document-and-table application whose API uses HTML for canvas content; Airtable is record-first and supports a constrained Markdown dialect inside rich-text fields. For Kipp’s mix of long-form knowledge, linked tasks, and eventual retrieval, Notion is the strongest default.

Why Notion wins for Kipp

  • It preserves the agent’s natural document interface. Kipp can round-trip a page through Notion’s supported enhanced-Markdown endpoints, rather than converting Markdown to Coda HTML or squeezing it into Airtable field values. This is not perfect CommonMark portability—Notion extensions must be handled—but it is a real, documented read/write contract.
  • It combines a real KB with a real task system. An Idea can have a long-form page body while also relating to Tasks, Projects, and Sources. Airtable wins at structured tracking but loses the page-shaped knowledge experience; Coda is flexible but its document logic and page-content API are a poorer durable agent contract.
  • Its Free plan fails later for this specific solo start. A one-member Notion workspace has unlimited blocks and its integration API is usable. Coda is also generous for an unshared document, but collaboration abruptly constrains its doc shape; Airtable’s 1,000 monthly API calls are especially easy for an automated capture/retrieval loop to exhaust.
  • The operational trade-off is manageable. Notion’s 3 rps rate requires a queue, but Kipp is a personal tool and does not need high throughput. Store Kipp IDs, use property filters before fetching bodies, cache/index asynchronously, and export Markdown periodically.
Important caveat: choose Airtable instead only if Kipp becomes primarily a structured tracker with short notes and form-driven capture. Choose Coda instead only if the main value is programmable personal dashboards/formulas and you accept HTML-based canvas writes. Neither condition is the current “personal KB that an agent can read and maintain” brief.

Alternatives: benefits and trade-offs

1. Notion databases + pages Recommended for this brief

Model: an Ideas database with relations to Projects, Tasks, Sources, and a knowledge-page hierarchy. Kipp maps the current idea schema to database properties and block children.

Pros: the best polished all-in-one experience here for notes, database views, filters, relations, and personal task/project tracking; mobile and sharing are excellent; users can reorganize without asking Kipp to change filesystem paths; an API and integrations make it viable for agent ingestion.

Cons: Notion now has native enhanced-Markdown create/read/update endpoints, but its format extends CommonMark with XML-like tags for Notion-only constructs; properties and database schema remain API objects rather than Markdown frontmatter. Unsupported blocks appear as <unknown>, and extremely large pages can be truncated. The documented API average is 3 requests/second, so a background ingestion queue is still essential.

Free plan—confirmed usable for Kipp: one-person workspaces have unlimited pages and blocks. The enhanced-Markdown endpoints are available to public, internal, and personal integrations, so Kipp can create, read, and update content without a paid plan. The ordinary API limit (about 3 requests/second) still applies, so Kipp should queue and retry.

What forces a paid upgrade: add a second workspace member and the Free workspace is capped at 1,000 blocks; need uploads larger than 5 MB (including a bot’s direct FileUploads, capped at 5 MiB in Free workspaces); need restoration beyond 7 days; need more guest capacity; or need the paid offline-page capability. These are product limits, not agent-integration limits. Kipp’s own LLM/API cost is separate from the Notion subscription.

Cost/limits: a one-person Free workspace is intended for personal projects/tasks; paid plans add history, collaboration, and controls. Avoid depending on bundled AI pricing for Kipp. Workspace-level cloud permissions are convenient, but the data and encryption keys are vendor-managed.

2. Private Git-backed Markdown vault + GitHub Issues/Projects

Model: ideas/{id}.md, notes/{slug}.md, and archive/{id}.md, each with YAML frontmatter (id, status, tags, created_at, task_url). GitHub Issues is the action ledger; a GitHub Project is the view. Kipp writes a single record at a time and can link the issue URL in frontmatter.

Pros: native Markdown; no new runtime vendor; every item has a stable path and Git history; works with rg, a static index, embeddings, or a vector service; GitHub Issues are externally trackable with API, comments, status, labels, and reminders/automation; private repository permissions and PAT scoping are already understood by the codebase.

Cons: for the current remote implementation, every Contents API mutation produces a Git commit—routine capture and workflow state updates would pollute history. The API is rate-limited and not transactional across multiple files; GitHub’s issue UI is developer-flavored; file semantics require a clear naming/metadata convention; GitHub is not end-to-end encrypted; a large vault needs an indexing job rather than one database query.

Cost/limits: GitHub Free includes private repositories, Issues, and Projects. Treat the authenticated REST API’s standard quota and secondary abuse limits as a design constraint: batch reads, cache, and retry with backoff. It is viable for deliberately batched or human-authored notes—not a good default event store for Kipp’s frequent mutable state.

3. Obsidian vault + Git or Obsidian Sync

Model: the vault is the canonical folder of one-file-per-idea/knowledge note. Kipp accesses the Git remote (or a small service that owns the vault); Obsidian supplies human authoring, links, search, and database-like views. GitHub Issues or another task tool is still recommended for externally tracked TODOs.

Pros: strongest fit for long-lived personal knowledge and future vector/search retrieval: notes are local, plain Markdown files with no required database; folders, tags, links, and properties solve random access; no API rate limit on the file format; easy exit and backup; Obsidian’s app is free for personal use.

Cons: not a hosted API platform by itself—remote writes must go through Git or a self-hosted bridge; task management is plugin-driven and weaker for external tracking; plugin quality/security is variable; Git sync is awkward for binary attachments and simultaneous edits; Obsidian Sync has plan-specific storage/file-size caps.

Cost/limits: local use is free. Optional Sync is a subscription; its published plans cap per-file size and total vault storage, while a Git remote or other sync method changes those limits. This is the best human knowledge-base option, but it should be treated as a client—not a backend SDK.

4. Linear

Model: Ideas become issues with templates, labels, project/cycle relationships, and long-form descriptions; a separate knowledge system retains durable reference notes.

Pros: exceptionally good operational TODO discipline, triage, statuses, projects, and external visibility; strong GraphQL API, webhooks, and predictable entity model; a good choice if “Kipp as a personal work manager” matters more than “Kipp as a second brain.”

Cons: poor canonical knowledge-base fit—rich issue bodies are not portable Markdown files and long research/drafts become awkward; requires a second system for documents and semantic retrieval; paid tiers become relevant sooner; not local-first.

Cost/limits: use its Free plan only to validate the workflow, then price the paid personal seat deliberately. OAuth requests are documented at 5,000/hour per user, with endpoint/complexity limits; API-key access is lower. Webhooks—not polling—are the intended integration pattern.

5. Coda

Model: a document combines pages, tables, buttons, formulas, and related task/idea rows. Kipp uses the Coda API to create and update rows and page content.

Pros: unusually flexible all-in-one document/database model; strong views and formulas make idea triage pleasant; tasks can link directly to source rows; it imports/pastes basic Markdown in the UI and has both an API and MCP path for agent work.

Cons: Coda does not offer Notion-style Markdown read/write endpoints: its API creates canvas content as HTML/rich text, so Markdown would require Kipp-side conversion and is not the canonical agent interface. Complex formulas can become an application inside an application; API access stops for docs above 125 MB; content writes are relatively slow (3 per 10 seconds).

Free plan: a personal, unshared Free doc has no page/object-count cap. Sharing changes that to 50 objects and 1,000 table rows per doc. Upgrade for more than 7 days of history, files above 10 MB (or more than 1 GB/doc total), more than 35 scheduled or 100 event automations/month, or a larger shared workspace. General API writes are 10 per 6 seconds; content writes are 3 per 10 seconds on every plan.

6. ClickUp

Model: ideas are tasks or Docs linked to tasks, organized in Spaces/Folders/Lists; Kipp writes through the public REST API and can subscribe to webhooks.

Pros: strongest all-in-one task execution option; Docs, wikis, task views, custom fields, and automations cover a broad personal system; API is available on all plans, and Docs supports import/export of core Markdown constructs.

Cons: feature breadth can be overwhelming for a single-person knowledge base; Docs’ Markdown import/export drops some rich constructs; the canonical data model is cloud/vendor-owned, so export discipline matters.

Cost/limits: Free Forever exists, with feature usage limits; the public API is 100 requests/minute per token on Free, Unlimited, and Business plans. A solid choice when task management is central rather than incidental.

7. Airtable

Model: structured bases for Ideas, Tasks, Sources, and Projects, with linked records and interfaces; long-text/rich-text fields carry drafts and references.

Pros: excellent record-level organization, filtering, linked relations, forms, and automation; API integration is straightforward; an agent can query exactly the records it needs rather than parse a document; external tasks can be first-class records.

Cons: it is a database/workspace rather than a pleasurable long-form writing tool. Its rich-text long-text fields and API use a limited Airtable Markdown dialect—not a full page-level Markdown import/export API—so complex knowledge needs field mapping and syntax testing. Full semantic retrieval needs a separate index; paid limits can surface as the base grows.

Free plan: credible for a small personal base, but an agent must be frugal: 1,000 records per base, 1 GB attachment storage per base, 1,000 API calls per workspace per month, and two-week revision/snapshot history. The API rate is 5 requests/second per base on all tiers. Upgrade when record/attachment capacity, history, automations/features, or especially monthly API calls become binding. Best for users who prefer views, fields, and forms to a document hierarchy.

8. Plane

Model: work items hold ideas and tasks, while projects, cycles, modules, and pages provide planning and knowledge context. Kipp uses Plane’s REST API and webhooks, or a self-hosted instance.

Pros: modern issue/task workflow, documented REST API, webhooks, cursor pagination, and a direct self-hosting route; good security story through scoped/expiring API keys or OAuth; more purpose-built for agent-driven work management than a generic note tool.

Cons: project-management-first rather than a mature personal knowledge base; Markdown portability is service-level rather than file-native; it can be heavier than needed for one person; Cloud-vs-self-host choice adds an operational decision.

Cost/limits: the available cloud/self-hosted tiers should be verified at selection. Its API has 180+ endpoints and webhooks, giving Kipp enough surface area without polling.

9. OpenProject

Model: work packages represent ideas/tasks, with projects, wiki pages, relations, and custom fields; Kipp integrates through its REST API or a self-managed deployment.

Pros: open-source, self-hostable project/knowledge environment with mature permissions; strong work-package tracking, wiki documentation, and relationship organization; avoids SaaS lock-in and suits a future shared system.

Cons: materially heavier and less polished for casual personal capture; deployment, upgrades, backups, and search are the owner’s responsibility when self-hosted; Markdown/wiki formatting is less portable than a vault.

Cost/limits: Community self-hosting can keep software cost low, while managed plans buy operational convenience. Scale is more than adequate; the practical cost is administrative attention.

10. Trello

Model: a board serves as an idea inbox/task system; cards hold Markdown-formatted descriptions, checklists, labels, due dates, attachments, and links to longer knowledge material.

Pros: the quickest low-friction external TODO tracker; cards are independently addressable, searchable, and easily automated; robust REST API and webhooks make Kipp integration simple; Free is useful for personal boards.

Cons: weak for deep, interlinked knowledge and long-form drafting; board/list structure can become a visual filing cabinet; Markdown is card-content formatting, not a portable knowledge corpus; export automation is a paid/experimental capability.

Cost/limits: its documented API allowance is 100 requests per 10 seconds per token and 300 per 10 seconds per key. Board/card object limits exist, but are far beyond this personal use case.

Recommended target design (not an implementation plan)

  1. Canonical records: use a Notion Ideas database with Kipp ID (unique, immutable, human-readable—for example KIPP-0042), Title, Aliases, Status, Created at, Updated at, and relations to Tasks, Projects, Sources, and other notes. Keep the free-form knowledge/draft in the page body; do not place many ideas in one body.
  2. Resolution before reads or writes: maintain a compact Kipp metadata index containing Kipp ID, normalized title, aliases, Notion page ID, status, and update timestamp. Resolve exact IDs first; then exact normalized titles; then score title candidates. If multiple plausible titles remain, present the candidates and require a selection. Only the resolved page ID may be mutated.
  3. Task responsibility: start with a related Notion Tasks database so every future TODO is visible independently, can carry a due date/status, and links back to its source idea. Reconsider Linear only if task operations become the dominant workflow.
  4. Agent retrieval: use property filters/search on metadata to identify candidates, then retrieve the selected page through the native enhanced-Markdown endpoint. Maintain an export-derived keyword/vector index as a discovery cache, never as the canonical record or mutation target.
  5. Portability: schedule Markdown export/backups to a private location. A Git repository is appropriate here as a periodic immutable snapshot/history, not as the hot path for every capture or status transition.
  6. Guardrails: use a dedicated Notion integration with access only to the intended pages/databases, queue writes below the published API rate, make operations idempotent with the Kipp ID, and log/retry failures without duplicating pages.
Decision checkpoint: choose Obsidian instead when local Markdown/offline ownership matters more than integrated external task tracking. If Kipp later requires cross-record transactions or high-volume retrieval, conduct a separate database-backend design; it is not one of these ten all-round productivity candidates because it fails the Markdown/TODO threshold. Git remains a strong backup/export path, but not the default primary store for Kipp.
