Shared workflow foundation and strict LinkedIn parity. This is the implementation-ready plan for Phase 1 of the Calendar architecture roadmap.

The migration is a clean cutover. Before deployment, the sole user will ensure no existing LinkedIn draft is awaiting feedback; no legacy GitHub-routing compatibility bridge will be retained.

2. Target architecture and contracts

Session and interaction contract

Cloudflare Workflow step results remain the durable state for an active LinkedIn session. Add a serializable, discriminated interaction event that carries an opaque interaction ID, version, action, Telegram update ID, and optional text. The workflow keeps the currently expected interaction ID and version; it ignores any delayed or duplicate event that does not match that current expectation.

type WorkflowInteraction = {
  interactionId: string
  version: number
  telegramUpdateId: number
  kind: "approve" | "revise" | "revision-feedback"
  text?: string
}

This type is internal, provider-neutral, and contains no Calendar or future-memory fields.

Tool registry, guard, and context contracts

Add zod as the single runtime-schema source. A source-controlled ToolDefinition has a stable name, description, Zod input/output schemas, privacy classification, and deterministic handler. A workflow’s allowlist is an explicit compile-time list of registry names. Configuration and model output cannot expand permissions.

ToolGuard.execute() verifies the allowlist and input schema before invoking a handler, then verifies the output schema before returning a result to a provider conversation. It returns redacted, safe failure categories rather than raw integration failures. The handler remains the only code that can mutate an integration.

Add a named asynchronous ContextProvider interface that returns only redacted context. Register no persistence, memory, preference, or retrieval implementation in this milestone.

LinkedIn permission decision: LinkedIn’s production allowlist is explicitly empty in Milestone 1. Its existing GitHub, Telegram, and LinkedIn integration calls remain deterministic workflow code. Only a later milestone may expose workflow-specific tools to the model.

Provider contract

Keep the existing GenerateFn text adapter so current LinkedIn agents do not need to change their orchestration API. Add a normalized provider client that supports canonical messages, declared tools, assistant tool-call parts, tool-result parts, text, usage, and provider-safe errors.

ProviderAdapter responsibility
DeepSeekMap canonical messages and Zod-derived JSON Schema to OpenAI-compatible tools; parse native assistant tool_calls and map tool result messages back to the provider wire format.
GeminiMap declarations to native function declarations; parse native function calls and map function responses back to Gemini content parts.

Provider modules remain the only layer that knows native provider shapes. In this milestone the new tool protocol is exercised by contract tests, not by LinkedIn production behavior.

Privacy-safe observability

Emit structured JSON to Worker console logs only. Records contain opaque correlation/session/interaction IDs, workflow name, event or tool name, outcome category, duration, and bounded retry count. They must omit raw Telegram text, draft content, Calendar content, provider payloads, OAuth material, tokens, and error bodies. Analytics Engine and dashboards are deferred.

3. Interaction Router Durable Object

Add InteractionRouterDO and bind it as INTERACTION_ROUTER. Keep the existing legacy Wrangler migration configuration and add a v2 new_sqlite_classes migration for this class; do not migrate to Wrangler’s newer declarative Durable Object export model in this change.

Use one router object per Telegram chat, derived from the chat ID. This isolates future users while avoiding a global router bottleneck. It stores only:

  • the Telegram chat ID and bot message ID;
  • an opaque callback/action token;
  • the target Workflow instance, expected interaction kind, version, expiry, and delivery state.

It never stores request text, drafts, Calendar payloads, OAuth data, or long-term preferences.

InteractionRegistration and resolution
Approve / Revise callbackGenerate a random opaque token before the message is sent. After Telegram returns its bot message ID, register the token, message ID, action, and expiry. Callback data contains only the opaque token; the webhook verifies chat and message identity before dispatch.
Reply to bot messageMap the reply target bot-message ID to its registered interaction. This always takes precedence over chat-level plain-text routing.
Typed revision feedbackMaintain one active plain-text revision interaction per chat. Starting a newer revision atomically invalidates the prior active plain-text interaction. Ordinary text maps to that active interaction.

Router registrations, claims, and acknowledgements are idempotent. A duplicate Telegram update reuses the same opaque event identity; expiry, consumed tokens, mismatched chats, stale versions, and unknown tokens perform no Workflow dispatch. A transient delivery failure leaves the interaction safely retryable without permitting a distinct action.

Retention and cleanup: expiry is enforced when resolving an interaction, and the router must also perform bounded physical cleanup during normal registration and resolution: delete expired rows and consumed rows past a short retention period. This avoids an unbounded per-chat SQLite index without introducing alarms, cron, or a separate cleanup workflow in Milestone 1.

4. LinkedIn migration sequence

  1. Restore baseline first. Diagnose every current red test against the documented authorization policy. Update only stale fixtures and expectations—for example, tests that expect the permitted insecure local fallback must explicitly use development mode. Preserve production authentication and failure behavior. The baseline gate is pnpm check green before the routing refactor begins.
  2. Add runtime modules and tests. Introduce Zod, the registry, guard, provider extensions, context interface, logger, router client, Durable Object class, binding, and v2 migration. Use focused unit tests before wiring LinkedIn.
  3. Adapt workflow state. Keep the existing LinkedIn payload and visible state transitions, but hold the expected interaction ID/version in the Workflow’s serializable step state. Continue using bounded step.do() and waitForEvent() calls.
  4. Register interactions after notification. The Telegram notification step sends the existing draft and controls, receives the bot message ID, then a durable idempotent registration step stores the router mapping. Workflow retries must reuse the same opaque action values.
  5. Replace webhook routing. Resolve callbacks, replies, and active typed feedback through INTERACTION_ROUTER; dispatch the normalized event to the existing Pipeline Workflow. Remove GitHub reads/writes whose only purpose is botMessageId or pendingRevision routing.
  6. Preserve deterministic approval. On a matching approval event, use the existing deterministic token lookup and LinkedIn draft creation path. Model behavior does not control publication. Existing status updates, archive behavior, cost calculations, messages, and safe error responses remain unchanged.
  7. Harden router retention. Add bounded, idempotent deletion of expired and old consumed interaction rows on normal router operations. Cover both logical expiry (no dispatch) and physical removal; do not add a scheduler or alarm for this milestone.
  8. Document and validate. Update the architecture roadmap after validation to mark Milestone 1 complete, and document the interaction-router binding and clean-cutover deployment condition.

6. Acceptance and rollout

  • pnpm check and the integration suite pass with no unrelated test failures.
  • Every new interaction is routed without GitHub-backed reply lookup or chat-level pendingRevision state.
  • Stale, mismatched, expired, and duplicate Telegram interactions cannot cause an approval, revision, or LinkedIn mutation.
  • LinkedIn remains fixed-orchestration with no production model tools and no visible regression in commands, draft lifecycle, approval, revision, publishing, privacy, or safe failures.
  • DeepSeek and Gemini expose the same normalized native-tool contract, ready for Calendar in Milestone 2.
  • Use the separate dev bot for a smoke flow: generate a draft, request and send revision feedback, approve it, and verify the existing LinkedIn draft outcome and Telegram messages.
  • Deploy only after confirming there are no existing LinkedIn drafts awaiting feedback; no legacy bridge is required.

7. Recorded decisions

  • Zod is the runtime schema source.
  • Router records live in a SQLite-backed Durable Object, partitioned by Telegram chat; Workflow state retains active session data.
  • Worker console logs are the initial observability sink.
  • One typed revision interaction may be active per chat; a newer one replaces it.
  • There is no in-flight compatibility bridge; the user performs a clean deployment cutover.
  • LinkedIn has an explicit empty tool allowlist until its later native-tool-loop milestone.
