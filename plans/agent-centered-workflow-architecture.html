Kipp — Agent-Centered Workflow Architecture Plan

Refactor Calendar from a terminal proposal extractor followed by a code-authored conversation into a bounded, tool-using agent. Preserve the completed Milestone 5 recurrence and integration baseline, and align LinkedIn with the same session contract without changing its approval or publishing behavior.

Outcome: for each Telegram interaction, the model interprets the conversation, uses guarded read and evaluation tools when helpful, and reaches exactly one workflow-approved terminal state: a validated plan ready to create or a clear request for all information still needed.

2. Approved architecture decisions

DecisionApproved contract
A1 — Mutation boundaryThe agent hands off ready_to_create { planId }. It never calls Google Calendar mutation directly. The workflow resolves, freshly revalidates, and idempotently writes the workflow-owned plan.
A2 — Calendar read projectionA bounded listing tool may expose opaque reference, title, start/end, all-day state, and transparency from the primary calendar. Descriptions, locations, attendees, organizers, conferencing data, links, credentials, and raw API responses remain excluded.
A3 — Complete validation feedbackZod and deterministic validators return every independently discoverable typed issue in one evaluation. The model asks for all actionable missing or invalid facts in one concise message.
A4 — Tool topologyCalendar exposes one purpose-limited event listing tool and one comprehensive candidate-evaluation tool rather than delegating policy across many small model-directed calls.
A5 — Durable conversationDuring the existing 15-minute interaction window, persist canonical structured state plus a bounded native user/model/tool transcript. Omit reasoning and compact obsolete event-list payloads. Expiry abandons and discards the pending interaction.
A6 — PresentationThe model writes normal clarification and conflict explanations. Code owns fixed action labels, operational failures, OAuth recovery, timeouts, and successful-write confirmation templates.
A7 — Button executionFixed, guard-authorized button choices transition workflow state deterministically. Natural-language replies and Edit corrections resume the agent.

5. Shared session and terminal contracts

Add a shared bounded agent-session result that carries the projected native messages, usage and execution metadata, and a workflow-specific terminal result. Avoid a universal business-outcome enum: Calendar and LinkedIn share mechanics while retaining their own terminal schemas.

AgentSessionResult<Terminal> {
  terminal: Terminal | null
  messages: ProjectedToolConversationMessage[]
  completed: boolean
  failureReason?: bounded runtime failure
  providerTurns, toolCallCount, toolNames, toolExecutions, usage
}

CalendarTerminal =
  | ready_to_create { planId }
  | needs_user_input {
      message
      reasonCodes[]
      interaction:
        | reply { requestedFacts[] }
        | choices { optionIds[] }
    }

LinkedInTerminal = ready_for_review { response }
  • ready_to_create succeeds only for an unexpired plan ID issued by the current interaction version.
  • needs_user_input may be called directly for model-detected language ambiguity. After evaluation, its issue and option references must match the evaluator’s authorized result.
  • Messages persisted for later turns exclude provider reasoning content. Tool execution logs retain only safe metadata already supported by the runtime.
  • The current three-turn/four-call limits and required terminal-handoff repair remain fail-closed runtime policy.

evaluate_calendar_candidate

  • Input is a discriminated one_off or recurring union. Each branch retains its own strict schema; RecurringProposal preserves explicit absence/default states.
  • Zod returns aggregate safe paths and expectations for malformed input. The handler never runs for structurally unsafe values.
  • The handler collects every independent semantic issue it can establish. Checks whose prerequisites are invalid are skipped rather than producing misleading secondary errors.

  • No validation or availability function returns English. Outputs use typed issue codes, safe parameters, summaries, and opaque identifiers.

7. Plan authorization and stale-state safety

  1. Evaluation creates version-scoped opaque plan and option IDs inside workflow-owned durable state. IDs reveal no event or Telegram data.
  2. A plan records the exact proposal, resolved one-off slot or recurring occurrence set, RRULE, exception set, reminder, evaluation version, and expiry.
  3. Terminal guards accept only IDs issued by the active evaluation. Superseded, forged, consumed, expired, or wrong-version IDs fail as invalid-state.
  4. Immediately before mutation, rerun the relevant deterministic policy and availability checks against fresh Calendar data. Do not let the model replace or amend the stored plan at this boundary.
  5. If the plan changes, consume neither the plan nor a write identity. Feed a typed availability_changed result into a fresh bounded agent session so it can explain the new state; use a deterministic fallback if the provider is unavailable.
  6. After a successful write, atomically mark the plan consumed and persist a trusted write_succeeded workflow event plus the complete edit baseline. Existing stable event identity and compensation behavior remain authoritative.

8. Conversation persistence and Telegram presentation

  • Persist the original request, real user replies, assistant messages, safe tool calls/results, terminal outcomes, canonical proposal state, current evaluation, and created-event baseline for at most 15 minutes.
  • Do not persist provider reasoning. After a terminal handoff, replace obsolete event-list item arrays with range/count/truncation metadata once the current evaluation has captured the needed facts. Canonical domain state, not prose, remains authoritative.
  • The model composes normal requests for missing information and explanations of conflicts or choices. It receives safe typed facts rather than English fragments from validators.
  • Code maps option IDs to fixed labels such as Use this time, Create with adjustments, Try another time, and Cancel. The model cannot invent a button or bind a label to a different action.
  • Use/confirm/cancel/retry button taps transition deterministically. A reply requested by the agent and an Edit correction append real user input and begin a new bounded agent session.
  • Successful writes use trusted templates populated from the persisted result. The next Edit session receives the structured created baseline without an extra LLM rendering turn.
  • OAuth recovery, timeouts, exhausted tool sessions, provider failures, and post-write delivery recovery retain concise deterministic fallbacks.

9. Calendar migration sequence

  1. Typed domain results: replace English-returning one-off and recurrence validation with aggregate issue collectors. Keep pure scheduling and recurrence behavior unchanged and add compatibility adapters only while the workflow migration is incomplete.
  2. Projected Calendar reads: add the bounded events.list integration and its schema-checked tool projection without changing FreeBusy-based authorization.
  3. Evaluation and plan store: assemble strict one-off/recurring inputs, deterministic evaluation outcomes, opaque plans/options, version binding, consumption, and fresh revalidation.
  4. Agent session: replace submit_one_off_proposal, submit_recurring_proposal, and request_clarification as the only available terminal actions with list/evaluate plus the two approved terminal handoffs.
  5. Durable conversation: persist projected native messages and canonical state across waits; remove synthetic question/reply concatenation and prose-dependent pending-conflict fields.
  6. Workflow simplification: replace normal hard-coded clarification/conflict branches with terminal-outcome handling while preserving deterministic buttons, auth recovery, mutation, compensation, confirmation, and Edit.
  7. Remove compatibility paths: once direct, conflict, recurrence, reconnect, and Edit integration coverage passes, delete English adapters and obsolete conversational helpers.

10. LinkedIn alignment

LinkedIn is already close to the target: it runs a bounded native-tool session, persists its transcript, and hands a complete response to deterministic review and publishing. Adapt it to the shared session-result contract with ready_for_review; do not redesign the user experience.

  • Keep Telegram approval, revision waits, publishing authorization, archival behavior, and failure handling deterministic.
  • Keep real feedback appended to the native conversation transcript.
  • Verify repository-wide imports before removing legacy draft/critique/revise/classify modules. Remove them only when production code no longer depends on them and parity tests pass.

12. Completion criteria

  • Every normal Calendar interaction ends in a schema-validated ready_to_create or needs_user_input handoff.
  • No domain validator or availability engine returns user-facing English.
  • The model can read only the approved bounded Calendar projection and cannot authorize or parameterize a mutation outside an issued plan.
  • All action buttons bind to deterministic, guard-authorized IDs; all natural-language replies resume with real bounded conversation context.
  • Clear requests still auto-create, successful writes still offer immediate Edit, and no provider or delivery failure can duplicate an event.
  • Calendar documentation states the new read-tool and language boundary consistently, LinkedIn passes parity coverage, and all Milestone 5 recurrence behavior remains intact.
