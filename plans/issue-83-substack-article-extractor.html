Structured Substack Article Extractor

Build a pure, Worker-safe module that turns one RSS item’s rich article HTML into the compact, section-aware JSON that the later RSS idea workflow will give its LLM.

This phase deliberately does not change RSS polling, agents, Notion, Telegram, cadence, or workflow behaviour. Those integrations belong to Issue #84.

1. Outcome and boundaries

Add a deterministic extractor at src/substack/article.ts. Given the title, optional subtitle, source URL, and complete HTML from one RSS item, it returns readable authored prose in source order, organized as an optional introduction plus first-order sections.

The extractor is a content projection, not a scraper or an agent capability. It has no network access, never follows URLs, never fetches a Substack page or undocumented API, and does not process images. It must be safe to import in the Cloudflare Worker runtime.

Phase boundary: Issue #83 establishes the extraction contract and proves it against real public RSS HTML. Issue #84 will supply RSS metadata, register the bounded article-reading tool, require that tool before idea generation, persist raw ideas, notify Telegram, and remove Substack ideas from cadence.

2. Public interface

Use linkedom/worker and export a parser with this input and output contract:

type SubstackArticleInput = {
  title: string;
  subtitle?: string;
  sourceUrl: string;
  contentHtml: string;
};

type SubstackArticle = {
  title: string;
  subtitle?: string;
  sourceUrl: string;
  sections: Array<{
    heading: string | null;
    content: string;
  }>;
};
  • Normalize title, subtitle, headings, and prose by decoding HTML entities, collapsing internal whitespace, and trimming surrounding whitespace.
  • Omit an empty subtitle. Preserve sourceUrl unchanged as supplied by the caller.
  • Join retained paragraphs within a section with exactly one blank line. The model deliberately has one concatenated content string rather than a block array.
  • Do not emit empty sections. Prose before the first H2 forms one introduction with heading: null.

3. Content projection rules

Source HTMLProjection
Prose before first H2One introduction section with heading: null.
H2Starts the next first-order section. Sections remain in source order.
H1Omit: title is dedicated RSS metadata, so repeating it adds no value.
ParagraphOne normalized paragraph in the current section.
H3–H6Retain as its own plain-text paragraph in the current H2 section. Do not create third-level hierarchy.
ListsRetain list items as readable •-prefixed lines without duplicating nested text.
Pull quotes and block quotesRetain as readable paragraphs.
TablesRetain each row as readable cell-delimited text.
LinksKeep visible link text only; never retain link destinations.
Unfamiliar ordinary wrappersTreat as transparent and retain normal authored text in source order unless clearly image, UI, or subscription content.

Traversal must consume semantic containers only once, so collecting a list, block quote, or table cannot also collect its nested paragraphs a second time.

4. Noise and markup policy

Remove non-content subtrees before traversal. The result contains no raw markup, UI text, class, ID, data attribute, CDN URL, image-derived content, or styling information.

  • Remove image markup and wrappers/captions: img, picture, figure, figcaption, and SVG.
  • Remove executable and styling markup: scripts, styles, and equivalent non-visible technical nodes.
  • Remove forms and controls: forms, buttons, inputs, selects, and text areas.
  • Remove known Substack subscription widgets and promotional calls-to-action, including their readable button and caption text.
Do not overfit to today’s markup: known UI and image containers are removed deterministically, but neutral div/span-style wrappers are not discarded merely because they are unfamiliar. That preserves author prose as Substack markup evolves.

5. Failure contract

Return a typed parse failure for each of these conditions:

  • blank or missing title;
  • absent or blank contentHtml; and
  • HTML that leaves no retained authored prose after cleaning.

One non-empty authored paragraph is sufficient for parser success. The later idea-generation phase decides whether the article has enough material for one or more worthwhile ideas; this module must not impose an editorial threshold.

6. Tests and validation

Committed real fixture

Commit the approved complete public RSS HTML fixture for The Reps We Are Losing, with title, subtitle, and source URL supplied as test metadata. Assert meaningful facts rather than an every-word output snapshot:

  • an introduction and nine H2 sections, in correct heading order;
  • subtitle handling, representative source prose, entity decoding, and paragraph ordering;
  • retention beyond 6,000 characters;
  • absence of captions, subscription text, image/CDN URLs, link destinations, raw markup, and attributes.

Compact synthetic fixture

Cover malformed-but-recoverable HTML, neutral wrappers, nested lists, inline links, pull quotes, tables, H3, figures/captions, and subscription UI. Assert readable non-duplicated output and the two-level hierarchy.

Negative cases and runtime checks

  • Test typed failures for missing title, missing body, and a body that retains no authored prose.
  • Run unit tests, lint, typecheck, and the Worker deploy dry-run. This proves the linkedom/worker import bundles for the production target.
  • Run the existing inspection script once against several long public posts and manually compare title, headings, paragraph count, and normalized length with the articles. Keep this live check out of normal tests.

7. Implementation sequence

  1. Add the typed input, output, and parse-failure contracts in src/substack/article.ts.
  2. Parse the RSS HTML with linkedom/worker, remove explicit non-content subtrees, then walk its remaining content in source order.
  3. Implement the two-level section accumulator and normalized text projection, with semantic-container consumption preventing duplicates.
  4. Add real and synthetic fixtures plus deterministic unit tests for output facts and failure cases.
  5. Run the project’s standard quality gates and a manual long-post inspection; address parser behavior only within this extraction boundary.

8. Research decisions retained for posterity

Article-body source: RSS content:encoded

The v1 body source is the rich HTML already embedded in the RSS item that triggered the run. On 2026-09-16, the configured public feed’s checked post contained its complete article structure—paragraphs, H2 headings, lists, pull quotes, tables, and images/captions—whereas RSS description was the subtitle, not an article-body substitute. This approach avoids another request and gives the agent content through one narrow, item-bound capability rather than general web access.

Option consideredDecision and why
Observed /api/v1/posts/{slug} JSONNot used. It offered clean body_html, and its inspected structure matched the RSS body apart from entity serialization, but it is undocumented and unversioned.
Public article pageNot used in v1. The inspected public page was server-rendered and had semantic article HTML, but it would add a request and page-specific extraction dependency. Keep it as a future fallback only if RSS proves incomplete.
JSON-LD, hydration data, browser rendering, or third-party extractionNot used. JSON-LD did not contain the body; the other routes add undocumented contracts, a browser binding and cost, or new credentials and external dependencies without solving an observed problem.

This is intentionally a single-source design, not a claim that RSS is a permanent platform contract. Per-item completeness checks and the long-post spot check detect insufficient feeds. A failed or over-limit article must fail explicitly, never be silently truncated or replaced with a description excerpt. Do not put full article bodies in routine operational logs.

HTML parser: linkedom/worker

Cheerio and linkedom/worker were tested against the same captured 27,042-character RSS post and a synthetic malformed-HTML fixture. Both produced the same ten-section result (introduction plus nine H2 sections), with 10,498 characters of normalized text; both decoded entities, retained visible link text without URLs, omitted captions and subscription UI, avoided duplicate nested text, and bundled successfully for the Worker.

CandidateMeasured Worker import probeDecision
linkedom/worker367.44 KiB upload; 87.35 KiB gzip. Its Worker-specific export is an explicit fit for the target runtime.Selected. Equivalent required output with the smaller measured import cost.
Cheerio679.60 KiB upload; 164.20 KiB gzip. Its parse5-based default offers stronger browser-tree equivalence, but that advantage was not needed for the known fixtures.Rejected for v1 because it added roughly 312 KiB uncompressed and 77 KiB gzip over LinkeDOM without a demonstrated content benefit.

The probe sizes measure the isolated import, not the final application bundle. The lasting rule is to retain the explicit content policy and realistic fixtures: parsing is interchangeable; deciding which content counts and preventing duplicate collection are the critical maintenance concerns. Reconsider the library only if future real fixtures expose a parsing-semantics gap or a Worker compatibility issue.

9. Assumptions and deferred work

  • content:encoded is the sole body source for this phase. There is no page/API fetch, fallback adapter, arbitrary URL access, or image handling.
  • RSS title and description metadata plumbing is owned by Issue #84; this module accepts them as already-supplied values.
  • Resource limits, native-tool registration, agent prompting, retrieval alerts, Notion saves, raw-only idea behavior, and cadence removal are all Issue #84 work.
  • The pre-implementation library comparison already selected linkedom/worker: it matched Cheerio’s extraction output on real and synthetic content while producing the smaller Worker bundle.
