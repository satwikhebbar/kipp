3.3 Pinned wire contract — Notion API Notion-Version: 2026-03-11

All requests send Notion-Version: 2026-03-11 (required on every request) and Authorization: Bearer <NOTION_API_KEY>. The queryable unit is the data source; a Notion database is a container that owns child data sources, and the query endpoint addresses the data source, not the database. Payloads below are the fixtures the unit tests and FakeNetwork assert against.

Markdown truncation semantics

There is no next_page_id / next_cursor in a markdown response. Very large pages (over ~20,000 blocks) return truncated: true; blocks that could not be converted to markdown (unsupported block types, or blocks the integration cannot access) are listed in unknown_block_ids (up to 100 ids) and render as <unknown …/>. The Notion docs' recovery flow re-fetches each unknown id as a page_id to retrieve the subtree; a re-fetch of an inaccessible block returns object_not_found (404).

Client policy in getIdea(id) — immediate failure, no recovery path:

  1. GET /v1/pages/:id/markdown. A 404 object_not_found (page inaccessible to the integration) throws NotionError.
  2. If truncated: true or unknown_block_ids is non-empty → throw NotionError. getIdea returns a body only when the response is complete and fully converted; a partial or placeholder-containing body is never drafted from.
  3. The refetch/merge path from the docs is not implemented: one reachable policy (fail) is kept over an unreachable recovery path. Idea bodies are self-authored and short (RSS sub-idea ≤ 300 chars, Telegram ≤ 4096, manual), so a truncated or partly-converted response signals a corrupted or oversized page and must fail loudly. If recovery is ever needed it is a separate, tested algorithm.
// Policy fixtures (client tests assert these):
// GET /v1/pages/:id/markdown → 404 object_not_found (page inaccessible) → NotionError
// GET /v1/pages/:id/markdown → 200 { truncated: true, … }              → NotionError
// GET /v1/pages/:id/markdown → 200 { unknown_block_ids: ["blk_…"], … }  → NotionError
// No nested-refetch/merge fixtures exist: the recovery path is removed.

3.5 Idempotency identity

unique_id is read-only and auto-assigned at page creation, so it cannot be the pre-create idempotency key. Instead, every producer supplies a stable external key, stored in the Idempotency Key rich_text property:

ProducerKey shape
RSS main idearss:{guid}:0 (0 = main)
RSS side idea (i-th)rss:{guid}:{i}
Telegram /addtg:{chatId}:{telegramMessageId}
Migrationlegacy:backlog:{oldId} / legacy:archive:{oldId}

Atomic runtime ingest — IdeaIngestDO

Lookup-then-create-then-reconcile is only eventual: two callers that both pass the lookup could both create and each start a workflow, producing duplicate drafts/publishes. Runtime creation and every workflow start therefore go through a new Durable Object IdeaIngestDO (binding IDEA_INGEST), whose storage is the commit point. Two kinds of record, one responsibility each:

  • ingest({ key, idea, startWorkflow }) — DO id ingest:{key}; adopt-or-create the page and persist the key→pageId mapping. If startWorkflow, it delegates the start to the page-keyed claim record below. Used by rss main, rss side, /add.
  • start({ pageId, ideaId, source }) — DO id claim:{pageId}; the single ownership record for a page's workflow. Used by the ingest delegation, cadence, and /generate.
Page create (safe)
  1. Read the key's record from DO storage.
  2. If no pageId recorded: query Notion by Idempotency Key; if a page exists, adopt it; else create the page via the Notion client, then persist { pageId }.
  3. A crash anywhere in step 2 is recovered on retry because step 2 re-checks Notion before creating — storage is the commit point and the create is lookup-guarded, so the page is exactly-once.
Workflow ownership and start — one record per pageId (crash-safe)

An external PIPELINE_WORKFLOW call cannot be atomic with a DO storage write, so workflow-start is its own durable state machine keyed by pageId, not by the entry point. The claim record claim:{pageId} holds { status: "unstarted" | "started", instanceId, lastRestartAt? } and derives the deterministic instance id instanceId = "kipp-" + sha256(pageId).slice(0, 32). Because every start route — RSS ingest delegation, cadence, /generate — funnels through this one record and id, a given page maps to exactly one Workflow instance regardless of how it was triggered.

Cloudflare Workflows accepts a client-supplied instance id (create({ id }); pattern ^[a-zA-Z0-9_][a-zA-Z0-9-_]*$, ≤ 100 chars) and createBatch is idempotent: an id already in use within retention is skipped, not duplicated. get(id).status() and instance.restart() provide inspection and repair.

Start procedure:

  1. If unstarted → call PIPELINE_WORKFLOW.createBatch([{ id: instanceId, params }]).
    • Batch returns the new instance → persist started + instanceId; return it.
    • Batch returns empty (id already exists — a previous attempt survived) → PIPELINE_WORKFLOW.get(instanceId); if errored/terminated, restart() it; persist started; return it.
    • Any other error propagates; the record stays unstarted and the caller's retry re-enters at this step.
  2. If started (fast path, incl. post-start repair) → get(instanceId).status():
    • errored/terminated → if now - lastRestartAt > WORKFLOW_REPAIR_COOLDOWN_MS (default 1 hour), restart() the same instance and persist lastRestartAt. A terminal failure after the started write is therefore repaired on the next start, not orphaned.
    • queued/running/waiting/paused/complete/unknown → return as-is. complete is never re-run: the work already finished.
    • Return { workflowInstanceId, alreadyStarted: true }.

The cooldown is a single field and comparison that makes concurrent repair callers idempotent (DO calls serialize; the second caller sees a fresh lastRestartAt and skips) and stops a permanently-errored instance from being restarted on every duplicate delivery. It is a constant, not a config knob; it can be raised if repair churn ever matters.

WindowRecord on retryOutcome
Crash before createBatch returnsunstartedRe-issue with the same deterministic id → exactly one workflow
Crash after create succeeds, before started persistedunstartedRe-issue: id already exists → batch returns empty → get adopts the same instance → exactly one workflow
Instance errored/terminated while unstartedunstartedget + restart() re-runs the single instance — self-healing, no duplicate
Instance errored/terminated after started persistedstartedFast path checks get(id).status() → restart() the same instance (cooldown-bounded) → repaired, still exactly one instance
createBatch throws (non-idempotency error)unstartedError propagates; caller retry re-enters and re-issues

Because the instance id is deterministic and pageId-keyed, and create is idempotent, no duplicate instance is ever created — no downstream workflow claiming is required. The workflow payload is the event passed to the instance: { pageId, ideaId, source, … } (for ingest, ideaId is known once the page is created, before the start is delegated).

Existing-idea starts (cadence and /generate)

Cadence and /generate can race to start the same existing raw idea; the Status transition happens only after generation, so it cannot guard two starts. Both call the page-keyed claim start({ pageId, ideaId, source }) — the same record and instance id RSS ingest uses. The first caller persists started; a concurrent caller re-enters and receives the same workflowInstanceId — exactly one workflow instance. A non-first caller can skip post-start work (e.g. cadence's publish-after-approval polling) using alreadyStarted.

Non-atomic paths

  • Migration runs as a single local process and bypasses the DO (direct createIdea), which is inherently single-threaded; it must not run concurrently with itself, and the cutover precondition (no awaiting-feedback idea) prevents overlap with runtime ingest.

4. Architecture and flow

4.1 Notion integration client (src/integrations/notion.ts)

  • Factory createNotionClient(env) using NOTION_API_KEY, NOTION_IDEAS_DATA_SOURCE_ID.
  • Endpoints used per §3.3: POST /v1/pages, PATCH /v1/pages/:id, GET/PATCH /v1/pages/:id/markdown, POST /v1/data_sources/:id/query.
  • Rate limiting: 350 ms minimum spacing between requests when NOTION_FREE_TIER !== "false"; a static NOTION_RATE_LIMIT_DELAY_MS constant controls the delay value.
  • Retry: 429/529/5xx honored with Retry-After and exponential backoff + jitter, max 3 attempts. Non-transient (400/401/403/404/409) throw a NotionError immediately.
  • Query pagination: loop start_cursor until has_more=false (bounded page count, e.g. max 100 pages); abort with NotionError if request_status.type === "incomplete".
  • Markdown retrieval per §3.3 policy: immediate failure on truncated: true, non-empty unknown_block_ids, or 404; never return a partial or placeholder body.
  • Property reads: unique_id parsed from properties["Kipp ID"].unique_id.number; Status from properties.Status.status.name.

6. Migration and rollback

6.1 One-time migration

  1. Manual setup first (see docs): create internal integration with the capabilities from §3.3, create the Ideas data source with the exact property schema from §3.1, share it with the integration. The schema is minimal and matches what this code writes; a property missing from the data source surfaces as a Notion validation error, so create all §3.1 properties before deploying.
  2. Run scripts/migrate-to-notion/ (self-contained parser + archive + migrate runner). It runs as a local Node script, outside the Worker Env, and reads its own configuration from the process environment: GITHUB_PAT, DATA_REPO_OWNER, DATA_REPO_NAME (selects the source data repo + authenticates the GitHub reads) and NOTION_API_KEY, NOTION_IDEAS_DATA_SOURCE_ID (authenticates and addresses the Notion writes).
    • Read ideas.md and archive.md from the GitHub data repo via the existing GitHub client.
    • For each idea, create a Notion page with mapped properties and body markdown, keyed by legacy:backlog:{oldId} / legacy:archive:{oldId}.
    • Deterministic idempotency: before each create, query by the legacy:… Idempotency Key and skip any already present. The Idempotency Key property is the persisted migration ledger — no separate ledger file. Rerunning after a partial failure creates only the missing pages. Single-threaded: it must not run concurrently with itself.
    • Report success/failure counts; do not delete ideas.md / archive.md.
  3. Deploy the new code. GitHub files become inert history.
ID continuity: Notion assigns new sequential Kipp IDs. Old GitHub IDs are preserved only as legacy: Idempotency Keys (Q14). A workflow must not be in-flight across the cutover — confirm no idea is in awaiting-feedback before migrating.

6.2 Rollback

Revert the code deploy (git revert of this branch's commits) and re-point. GitHub ideas.md/archive.md are untouched by migration, so the pre-Notion code path works unchanged. Data-loss boundary: Notion writes are not copied back to GitHub. Ideas created in Notion during the post-cutover window are invisible to the reverted GitHub path and must be re-added manually or accepted as lost; the migration ledger is Notion-only, so a rollback does not replay those pages into ideas.md.
