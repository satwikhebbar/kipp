Integration Testing Engineering Plan

Core Principle: Integration tests exercise real application wiring (handlers, orchestrators, parsers) with deterministic, stateful local fakes. They should never make real network calls to Telegram, GitHub, LinkedIn, or LLM APIs.
Integration boundary: Real app modules wired together; only platform/runtime edges (Cloudflare bindings, step.do, waitForEvent) and external HTTP (fetch) are faked. Neighboring app modules (providers, clients, parsers, archive logic, backlog managers) are not mocked.

1. Scope & Strategy

This plan introduces a contract-style integration testing suite bridging the gap between isolated unit tests and full manual End-to-End (E2E) tests. To minimize sprawl and setup complexity, we start by extracting existing mocking patterns into a reusable stateful harness, prioritizing the highest-value flows and security boundaries.

2. Phase 1: Reusable Stateful Fake Harness

Instead of building a completely new fake system from scratch, we extract the shared vi.stubGlobal("fetch", ...) patterns currently used in src/__tests__/telegram.test.ts and src/__tests__/workflow.test.ts.

We create src/__integration__/setup.ts which exposes a unified fake fetcher that maintains state across API calls. This stateful approach is critical because we need to assert data progression (e.g., an idea transitioning from raw to awaiting-feedback to archived) rather than simply asserting "fetch was called".

Public API

createFakeNetwork(overrides?: {
  githubFiles?: Map<string, string>
  llmResponse?: Record<string, any>
  rssFeedXml?: string
}): {
  fetch: typeof globalThis.fetch
  getState: () => FakeState
}

interface FakeState {
  githubFiles: Map<string, string>
  telegramMessages: Message[]
  linkedinDrafts: Draft[]
  llmResponses: Record<string, any>
}

// Additional helpers for Workflow tests
createFakeStep(): {
  do: typeof WorkflowStep.do
  waitForEvent: typeof WorkflowStep.waitForEvent
  getCalledSteps: () => string[]
}

createFakeWorkflowBinding(): {
  create: typeof Env.PIPELINE_WORKFLOW.create
  get: typeof Env.PIPELINE_WORKFLOW.get
  getCreated: () => Array<{ id: string; params: WorkflowParams }>
  getReceivedEvents: () => Array<{ instanceId: string; event: any }>
}

The fetch handler routes by URL path for GitHub API, Telegram API, LinkedIn API, RSS feed URLs, and LLM providers. githubFiles is pre-populated with style-prompt.md and any provided overrides. State is updated on each call (GitHub PUT, Telegram sent messages, LinkedIn draft creation).

Future improvement: As more stateful endpoints are added, make which state shape comes back configurable per endpoint. Not optimized for now.

Acceptance Criteria

  • setup.ts maintains an in-memory representation of GitHub ideas.md that can be updated via mock PUT requests and read via mock GET requests.
  • setup.ts captures outbound Telegram messages and exposes them for assertion.
  • setup.ts intercepts LinkedIn API requests and captures DRAFT creation payloads.
  • LLM responses are configurable to return deterministic JSON structures mimicking valid outputs.
  • RSS feed requests return configurable XML.
  • Fake step and fake Workflow binding allow testing WorkflowEntrypoint subclasses and handlers that call env.PIPELINE_WORKFLOW.*.

4. Phase 3: Script Configuration

Integration tests are kept separate from unit tests until stable. Real-service smoke testing is strictly opt-in.

"scripts": {
  // Standard vitest run (integration suite excluded via config)
  "test": "vitest run",

  // Explicit partition scripts
  "test:unit": "vitest run src/__tests__/",
  "test:integration": "vitest run src/__integration__/",

  // Real services must be explicit and NOT part of 'pnpm check'
  "test:smoke:real": "RUN_REAL_SERVICE_TESTS=1 vitest run scripts/local-workflow.test.ts"
}

Acceptance Criteria

  • pnpm test:integration runs cleanly in <5 seconds using only local memory.
  • pnpm check does not invoke test:smoke:real.
  • vitest.config.ts excludes src/__integration__/** by default.

Relationship to existing __tests__/: Unit tests (src/__tests__/) remain as focused scenarios with precise per-test mock expectations. Integration tests serve as the definitive "wiring is correct" safety net. Both are maintained in parallel.
